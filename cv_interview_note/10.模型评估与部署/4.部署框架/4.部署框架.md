# 4.部署框架

## 1.概述

训练好的模型（PyTorch 等）不能直接高效上线：要跨平台、要加速、要服务化。**部署链路**通常是：

```
训练框架                中间表示                 推理引擎/服务
┌──────────┐   导出   ┌──────────┐   编译/转换   ┌──────────────────┐
│ PyTorch  │ ──────> │  ONNX    │ ──────────> │ TensorRT / NCNN  │ ──> 上线
│ TF/Keras │         │ (opset)  │             │ OpenVINO / TFLite│
└──────────┘         └──────────┘             │ Triton 服务化     │
                                              └──────────────────┘
```

- **中间表示（IR）**：解耦训练框架与推理引擎，ONNX 是事实标准；
- **推理引擎**：针对硬件做图优化、算子优化、低精度；
- **服务化**：多模型管理、动态 batch、监控。

## 2.ONNX

### 2.1 作用

- **Open Neural Network Exchange**：开放模型交换格式；
- PyTorch -> ONNX -> TensorRT / OpenVINO / NCNN / onnxruntime ...一套导出多端部署；
- 定义了算子集（opset）与图格式（protobuf）。

### 2.2 opset

- 每个 opset 版本定义一组算子及语义，版本越高算子越全、语义越新；
- 导出时指定：opset 太低缺算子，太高老引擎不支持；
- 常用 opset 11~17（按目标引擎要求选）。

### 2.3 导出（PyTorch）

```python
import torch

model.eval()
dummy = torch.randn(1, 3, 640, 640)
torch.onnx.export(
    model, dummy, "model.onnx",
    opset_version=13,
    input_names=["images"],
    output_names=["boxes", "scores"],
    dynamic_axes={                    # 动态 shape：batch/尺寸可变
        "images":   {0: "batch", 2: "height", 3: "width"},
    },
)
```

### 2.4 动态 shape

- **静态 shape**：编译期固定，引擎可充分优化，速度最快；
- **动态 shape**：支持 batch/分辨率变化，通用但有优化范围（min/opt/max）与性能代价；
- TensorRT 需建 profile 指定各维 min/opt/max；
- 建议：形状集合有限时为每档各编译一个 engine。

### 2.5 onnxruntime

- 微软开源的 ONNX 推理引擎，跨平台（CPU/GPU/移动端）；
- 支持图优化（自动融合）、不同 provider（CPU/CUDA/TensorRT EP）；
- 快速验证与 CPU 部署的主流选择；

```python
import onnxruntime as ort

sess = ort.InferenceSession("model.onnx", providers=["CUDAExecutionProvider"])
outputs = sess.run(None, {"images": x.numpy()})
```

- 常用检查工具：`onnx.checker`、Netron（可视化）。

## 3.TensorRT

### 3.1 engine 编译

- ONNX 不能直接跑，需**离线编译**为针对具体 GPU + 精度 + shape 的 engine；
- 编译期做：图优化、算子融合、kernel 自动调优（计时选最优）、内存规划；
- engine 与 GPU 型号 / TRT 版本**绑定**，换卡换版本要重编（耗时分钟级）；

```bash
trtexec --onnx=model.onnx \
        --fp16 \
        --minShapes=images:1x3x640x640 \
        --optShapes=images:8x3x640x640 \
        --maxShapes=images:16x3x640x640 \
        --saveEngine=model.engine
```

### 3.2 plugin

- 遇到**不支持的算子**（自定义算子、新算子）时，写 plugin 接入自己的 CUDA 实现；
- 实现 TensorRT 的 plugin API（如 IPluginV2DynamicExt），注册后 parser 识别；
- 常见 plugin 化算子：检测后处理（如 YOLO 的 decode）、自定义注意力变体；
- 维护成本高（随 TRT 版本迁移），能改写为等价标准算子则优先改写。

### 3.3 FP16 / INT8

- `--fp16`：几乎无损、约 2× 加速，**默认开**；
- `--int8`：需校准数据（PTQ）或 QAT 导出的量化模型，约 4×；
- 混合精度：敏感层自动回退 FP16/FP32；
- 详见 [2.模型压缩](../2.模型压缩/2.模型压缩.md)。

### 3.4 timing cache 与 engine 复用

- kernel 自动调优耗时可观，**timing cache** 可缓存调优结果，重编加速数倍；
- `--timingCacheFile=trt.cache --useCache`；
- CI/生产中：同硬件缓存 + 固化 engine，避免每次全量编译。

## 4.OpenVINO

- Intel 官方推理引擎，针对 **CPU（含集成显卡）、iGPU、VPU** 优化；
- 链路：ONNX -> OpenVINO IR（xml + bin）-> 推理；
- 一行 API 模式转换：`ovc model.onnx`；
- 优势：Intel CPU 上免 GPU 依赖做高性能推理（IPC 场景、边缘盒子上常见）；
- 支持 FP16/INT8 量化（NNCF 工具，含 QAT/PTQ）。

## 5.移动端框架

### 5.1 NCNN

- 腾讯开源，**无第三方依赖**、库小，ARM 侧优化极深；
- 链路：ONNX -> NCNN（.param + .bin）；
- 大量手写 ARM 汇编/NEON 优化，手机 CPU 部署主流；
- 配套 ncnnoptimize 工具做量化（INT8/FP16）。

### 5.2 MNN

- 阿里开源，类似定位：移动端 + IoT，CPU/GPU(NPU) 均支持；
- 表达式/几何推理引擎设计，转换工具 MNNConvert；
- 与 NCNN 二选一，按业务生态选。

### 5.3 TFLite

- TensorFlow 官方移动端方案（.tflite，FlatBuffer 格式）；
- PyTorch 模型需经 ONNX -> TF -> tflite（链路长）或直接用 PyTorch Mobile/ExecuTorch；
- 支持 NNAPI / GPU delegate 调手机加速硬件；
- Android 官方生态集成好。

## 6.服务化：Triton Inference Server

- NVIDIA 开源的**推理服务框架**，管理多模型生命周期；
- 支持 ONNX / TensorRT / PyTorch / TF / Python backend 多种模型格式；

**核心特性**：

- **dynamic batching**：把短时间窗内的请求凑 batch 提吞吐（配置 max_queue_delay）；
- **concurrency**：多实例（instance group）打满 GPU；
- **ensemble / BLS**：多模型流水线编排（如 预处理 -> 检测 -> 后处理 串联）；

```
请求 ──> Triton ─┬─> 预处理模型(Python backend)
                 ├─> 检测模型(TensorRT)
                 └─> NMS 后处理 ──> 响应
                    (ensemble 串成流水线)
```

- HTTP/gRPC 接口 + Prometheus 指标，云上批量服务标配；
- LLM 服务化对应的是 vLLM/TGI 等（见 [llm_interview_note/06.推理](../../llm_interview_note/06.推理/)）。

## 7.框架选型对比

| 框架 | 平台 | 性能 | 量化 | 生态/备注 |
| --- | --- | --- | --- | --- |
| TensorRT | NVIDIA GPU | 极高 | FP16/INT8/FP8 | NVIDIA 端事实标准，engine 绑硬件 |
| onnxruntime | 全平台 | 高 | INT8 | 跨平台首选，CPU 也强 |
| OpenVINO | Intel CPU/iGPU | 高(Intel 侧) | INT8(NNCF) | Intel 无 GPU 场景 |
| NCNN | ARM 手机 | 高(ARM) | INT8/FP16 | 无依赖、库小 |
| MNN | 移动/IoT | 高 | INT8 | 阿里系 |
| TFLite | Android 为主 | 中高 | INT8/FP16 | TF 生态、NNAPI |
| Triton | 服务端 | -(调度层) | - | 服务化框架，本身可跑上述引擎 |

**选型路径**：

```
NVIDIA GPU  -> TensorRT(服务端可套 Triton)
Intel CPU   -> OpenVINO / onnxruntime
手机 ARM    -> NCNN / MNN / TFLite
快速验证    -> onnxruntime
```

## 8.部署常见问题

### 8.1 算子不支持

- **现象**：ONNX 导出或 parse 阶段报 unknown operator；
- **排查**：
  1. 提高 opset 版本（新版带新算子）；
  2. 改写模型为等价基础算子组合；
  3. 写 plugin（TensorRT）/ 自定义层（NCNN）；
  4. 升级引擎版本（新版 TRT 常补齐算子）。

### 8.2 精度对不齐（FP32 参考输出 vs 部署输出）

**排查步骤**：

```
1. 逐层对比: 同一输入下, 对比 ONNX 与 PyTorch 各层输出
   (torch.onnx.export 时可存每层输出, 或用 onnxruntime 逐节点跑)
2. 先确认 FP32 就对齐: 若 FP32 就飘, 多为预处理不一致
3. 检查预处理: BGR/RGB、归一化均值方差、resize 插值方式、量化缩放
4. 检查后处理: 坐标解码、NMS 实现、letterbox 还原
5. FP32 对齐后再开 FP16/INT8, 若掉点: 定位敏感层, 让其回退高精度
6. 数值容差: FP16 相对误差 ~1e-3 属正常, 不必逐位一致
```

- **常见根因**：颜色通道顺序、归一化参数、插值 align_corners、动态 shape 的 padding、自定义算子实现差异。

### 8.3 动态 batch 问题

- engine 未开动态 shape 时只能按编译 batch 跑；
- 请求 batch 不齐需 pad 到 max，浪费计算；
- 检测多分辨率输入建议按档位分 engine，或固定 letterbox 尺寸。

## 9.面试常考问题

**Q1：说一条完整的 CV 模型部署链路？**

- PyTorch 训练 -> 导出 ONNX（定 opset、shape）-> 目标引擎编译（TensorRT engine / NCNN）-> 集成预处理后处理 -> 服务化（Triton/自研服务）-> 监控上线。

**Q2：ONNX 在部署中起什么作用？**

- 中间表示，解耦训练与推理框架；
- 一次导出，多引擎使用；
- opset 决定算子集版本，导出时需与目标引擎匹配。

**Q3：TensorRT 的 engine 为什么要在目标机器上编译？**

- 编译期做 kernel 自动调优与内存规划，与具体 GPU 型号/TRT 版本绑定；
- 换硬件/版本需重编；可用 timing cache 加速重复编译。

**Q4：遇到 TensorRT 不支持的算子怎么办？**

- 升级 opset / TRT 版本看是否补齐；
- 改写为等价标准算子组合；
- 写 plugin 接入自定义 CUDA 实现；
- 或该子图 fallback 到 onnxruntime（混合执行）。

**Q5：FP16 部署精度掉了怎么排查？**

- 先确认 FP32 TRT 与 PyTorch 对齐（排除预处理问题）；
- 逐层对比找敏感层（attention、大值激活、归一化）；
- 敏感层强制 FP32（混合精度）；
- FP16 相对误差 1e-3 量级正常，看最终指标而非逐位。

**Q6：部署后精度与训练差很多，列出排查清单？**

- 预处理：BGR/RGB、mean/std、resize 插值、padding 方式；
- 后处理：坐标解码、score 计算、NMS 参数；
- 模型：opset 算子语义、导出是否 eval 模式（BN/Dropout）、自定义算子实现；
- 精度模式：FP16/INT8 敏感层；
- 输入：shape/dtype、动态范围。

**Q7：动态 shape 和静态 shape 怎么选？**

- 静态：最快（编译期全优化），输入尺寸固定时首选；
- 动态：灵活但慢，需设 min/opt/max profile；
- 常见折中：几个固定档位各编译一个 engine。

**Q8：NCNN/MNN/TFLite 各自适用场景？**

- NCNN：无依赖、ARM 深度优化，手机 CPU 部署主流；
- MNN：移动 + IoT，多后端（含 NPU）；
- TFLite：Android/TF 生态、NNAPI delegate；
- 都是"模型小、启动快、功耗低"取向。

**Q9：Triton 的 dynamic batching 是什么？适合什么场景？**

- 将时间窗内多个独立请求凑成一个 batch 推理；
- 摊薄权重加载开销，提高 GPU 利用率与吞吐；
- 适合高并发在线服务；延迟敏感场景需小窗口或关闭。

**Q10：onnxruntime 和 TensorRT 的关系？**

- 都是推理引擎，onnxruntime 跨平台、易用，CPU 也强；
- TensorRT 深度绑定 NVIDIA、性能极致；
- onnxruntime 可通过 TensorRT EP 调用 TRT engine（外层 API + 内层 TRT）。

**Q11：为什么推理前要 model.eval() 再导出？**

- eval 固定 BN 统计（推理模式）并关闭 Dropout；
- 否则导出的图带训练语义，结果不可复现、精度异常。

**Q12：如何验证导出的 ONNX 正确？**

- 同输入对比 PyTorch 与 onnxruntime 输出（allclose，容差 1e-4~1e-5）；
- onnx.checker 检查图合法性；
- Netron 可视化核对结构。

## 10.总结

- **部署链路**：训练框架 -> ONNX -> 引擎编译 -> 服务化；
- **ONNX** 是通用桥梁，opset 与动态 shape 是导出关键；
- **TensorRT**：NVIDIA 端极致性能，代价是 engine 绑定硬件 + plugin 维护；
- **移动端**：NCNN/MNN/TFLite 三选一，看生态与硬件；
- **服务化**：Triton 管 batching/多模型/流水线；
- **精度对齐**是部署最高频问题：预处理 -> 逐层对比 -> 敏感层回退，按清单排查。
