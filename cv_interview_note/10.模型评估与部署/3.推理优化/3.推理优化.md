# 3.推理优化

## 1.概述

模型训练好只是第一步，**上线还要又快又省**。推理优化围绕**降低延迟、提升吞吐、减少内存**展开。本章侧重 CV（CNN 为主）与通用推理引擎优化；Transformer / LLM 侧的推理优化（KV Cache、PagedAttention 等）见姊妹仓库 [llm_interview_note/06.推理](../../llm_interview_note/06.推理/)。

### 1.1 延迟与吞吐

- **延迟（Latency）**：处理**一个**请求的耗时（ms），实时检测等场景关键；
- **吞吐（Throughput）**：单位时间处理**多少**请求（QPS / images/s），服务化场景关键；
- 二者不一定同向：batch 增大吞吐升，单请求延迟也可能升；
- 关注口径：单流延迟 vs 并发吞吐，报告时必须说明。

### 1.2 内存带宽：常被忽视的瓶颈

- 芯片峰值算力高不等于模型跑得快，**数据搬运**（DRAM <-> SRAM）常是瓶颈；
- 算术强度（Arithmetic Intensity）：**FLOPs / 字节访存量**（FLOP/Byte）；
- **Roofline 模型**：

```
性能(FLPS)
   │        ▲ 峰值算力平台（计算受限）
   │       ╱
   │      ╱  斜率 = 带宽（访存受限区）
   │     ╱
   └────┴──────────────► 算术强度(FLOP/Byte)
     拐点 = 峰值算力 / 带宽
```

- 算术强度低于拐点：**访存受限**（如 1×1 卷积、逐元素算子、上采样）；
- 高于拐点：**计算受限**（如大 GEMM）；
- 优化前先判断瓶颈类型：访存受限优化布局/访存量，计算受限优化算法/精度。

## 2.计算优化

### 2.1 算子融合

- 将多个小算子合成一个大算子，减少 kernel 启动和中间结果读写；

```
不融合: Conv -> BN -> ReLU   （3 次读写显存, 3 次 kernel）
融合后: ConvBNReLU          （1 次读写显存, 1 次 kernel）
```

- **Conv + BN 融合原理**（推理时 BN 可折叠进卷积）：

$$
W' = W \cdot \frac{\gamma}{\sqrt{\sigma^2 + \epsilon}}, \quad b' = (b - \mu) \cdot \frac{\gamma}{\sqrt{\sigma^2 + \epsilon}} + \beta
$$

- **推理时 BN 免费**：训练完直接折进权重，这是"训练用 BN、推理看不到 BN"的原因；
- 常见融合：Conv+BN+ReLU、Add+ReLU、Softmax+Reduce、GELU 融合。

### 2.2 im2col + GEMM vs 直接卷积

- **im2col**：把卷积展开成矩阵乘（GEMM），复用高度优化的 BLAS/cuBLAS；
- **直接卷积**：专门写的卷积 kernel（如 cuDNN），无需展开；

| 维度 | im2col+GEMM | 直接卷积 |
| --- | --- | --- |
| 实现难度 | 低 | 高 |
| 内存占用 | 大（展开冗余） | 小 |
| 效率 | 依赖 GEMM 库 | cuDNN 高度优化 |
| 适用 | 通用框架（早期 Caffe） | cuDNN / TensorRT |

- cuDNN 会按尺寸/配置**自动选算法**（含 implicit GEMM、Winograd、FFT）。

### 2.3 Winograd

- 数学变换把卷积**加法化**，减少乘法次数；
- 3×3 conv、stride=1 场景理论乘法量降至约 **9/16**（F(2×2, 3×3)）；
- 限制：主要适用小核、stride 1；变换本身有额外访存，大通道才划算；
- cuDNN/TensorRT 内部自动启用，无需手工。

### 2.4 FFT 卷积（简述）

- 时域卷积 = 频域乘法，用 FFT 加速**大核**卷积；
- 核小时开销不划算，CV CNN（3×3 为主）很少用；
- 曾用于大感受野场景，现代基本被其他方案替代。

## 3.内存优化

### 3.1 内存池

- 推理时反复 malloc/free 开销大且碎片化；
- 框架（TensorRT/NCNN 等）启动时**预分配内存池**，推理期间循环复用；
- 好处：零运行时分配、碎片少、延迟稳定（无系统调用抖动）。

### 3.2 NHWC vs NCHW

```
NCHW: [N, C, H, W]  通道优先（PyTorch 默认）
NHWC: [N, H, W, C]  空间优先（TensorRT/ARM 常用）
```

- **NHWC 优点**：同一空间位置各通道连续，便于 SIMD 向量化（尤其 INT8 打包）、访存友好；
- **NCHW**：逐通道处理友好，某些框架/算子更自然；
- GPU 上 NHWC 常更快（TensorRT 默认），ARM 端 NHWC + 打包量化也常见；
- 代价：布局转换本身要拷贝，框架会做**全局布局传播**选择最优方案。

### 3.3 zero-copy 与 pin memory

- **zero-copy**：CPU 锁页内存直接被 GPU 访问，省一次主机到设备拷贝（小数据/嵌入式有用，大拷贝走 DMA 更快）；
- **pin memory（锁页内存）**：不可换出页的 CPU 内存，GPU 可 DMA 直达；
- 数据加载：

```python
DataLoader(dataset, batch_size=bs, num_workers=4,
           pin_memory=True)          # CPU -> GPU 拷贝更快
x = x.to("cuda", non_blocking=True)  # 配合异步拷贝
```

- 服务化场景：预处理放 CPU（多线程），推理放 GPU，流水并行掩盖拷贝。

## 4.图优化

推理引擎拿到计算图后做**图级变换**（编译期一次完成）：

- **常量折叠**：编译期能算的先算掉（如固定的 shape、拼接的常量参数）；
- **死代码消除**：删除不影响输出的节点；
- **公共子表达式消除**：相同计算只算一次；
- **布局转换传播**：选全局最优布局，减少中途转换；
- **算子替换**：等价换高性能实现（如 Conv+BN 折叠、PAD 并入 Conv）；
- **代数化简**：如 `x*1`、`concat 后 split` 抵消。

```
原始图:  x -> Pad -> Conv -> BN -> ReLU -> Dropout -> Output
优化后:  x -> ConvBnReLU(pad 并入 conv, dropout 推理期删除) -> Output
```

## 5.并行与调度

### 5.1 kernel launch 开销

- 每次 GPU kernel 启动有约几微秒的固定开销；
- 深层小网络（如轻量 CNN 移动端）大量小算子 -> **launch 开销占比高**；
- 对策：算子融合（减 kernel 数）、CUDA Graph（一次提交整图）、多 stream。

### 5.2 CUDA stream

- stream 内串行，stream 间可并行；
- 用途：多路视频流并发推理（各走独立 stream）；计算与拷贝重叠；
- 注意：单 stream 已经吃满 GPU 时多 stream 无收益甚至更慢。

### 5.3 动态 batch

- **请求级动态 batching**：把短时间窗内到达的请求凑成一个 batch，提高吞吐（如 Triton 的 dynamic batching）；
- 权衡：凑批越大吞吐越高，排队延迟也越高，需设 max queue delay；
- **batch 与延迟关系**：batch 增大摊薄权重加载（访存），吞吐上升；超过计算饱和点后延迟明显上升；
- CNN 对 batch 友好，检测模型需注意 padding 浪费。

### 5.4 异步与流水线

```
CPU: 预处理1  预处理2  预处理3 ...
GPU:        推理1    推理2    推理3 ...
(预处理与推理重叠，端到端吞吐 = max(CPU, GPU) 而非求和)
```

- 预处理（resize/归一化）常是隐藏瓶颈，多线程/多 stream 重叠。

## 6.模型级优化与分析工具

### 6.1 分析工具

| 工具 | 用途 |
| --- | --- |
| `nvidia-smi` / `dmon` | GPU 利用率、显存、功耗概览 |
| **Nsight Systems (nsys)** | 时间线：kernel、拷贝、CPU/GPU 重叠情况 |
| **Nsight Compute (ncu)** | 单 kernel 指标：带宽利用率、occupancy |
| PyTorch Profiler | 定位 Python/算子级热点，可导出 Chrome trace |
| TensorRT trtexec | engine 基准测试、逐层耗时分析 |

### 6.2 热点定位流程

```
1. nsys 看时间线: 是 GPU 忙还是 CPU 忙/等待?
2. GPU 忙 -> ncu 看最慢 kernel: 访存受限还是计算受限?
3. 访存受限 -> 融合、布局、量化(INT8)、减中间结果
4. 计算受限 -> 低精度、Winograd、换实现
5. CPU 忙   -> 减 launch(融合/CUDA Graph)、预处理下沉 GPU
6. 都闲     -> I/O 或调度问题(数据加载、串行拷贝)
```

### 6.3 PyTorch 侧快速优化

```python
model.eval()
with torch.no_grad():          # 关梯度
    ...
torch.backends.cudnn.benchmark = True   # 固定输入尺寸时自动选最优卷积算法
# 进一步: torch.compile / TensorRT 导出
```

- `cudnn.benchmark=True`：首次遍历各算法选最优，之后复用；输入尺寸多变时反而慢；
- `torch.compile`：算子融合 + kernel 优化（PyTorch 2.x）。

## 7.与 LLM 推理优化的关系

- **通用部分**：算子融合、低精度（FP16/INT8）、图优化、内存池、batch 调度；
- **LLM 特有**：自回归两阶段（prefill/decode）、KV Cache、PagedAttention、连续批处理、投机解码；
- CV 特有：分辨率可变（切图/金字塔）、NMS 后处理、图像预处理流水线；
- LLM 侧详见 [llm_interview_note/06.推理/llm推理优化技术](../../llm_interview_note/06.推理/llm推理优化技术/llm推理优化技术.md)。

## 8.面试常考问题

**Q1：延迟和吞吐的区别？如何分别优化？**

- 延迟：单请求耗时；吞吐：单位时间处理量；
- 降延迟：小 batch、算子融合、低精度、减少 launch 开销；
- 提吞吐：动态 batching、多 stream、流水线重叠预处理；
- 二者有权衡（凑 batch 升吞吐但增延迟）。

**Q2：什么是 roofline 模型？有什么用？**

- 横轴算术强度（FLOP/Byte），纵轴可达性能；
- 低于拐点访存受限，高于拐点计算受限；
- 指导优化方向：访存受限做融合/布局，计算受限做低精度/算法。

**Q3：为什么推理时 BN 可以融合进卷积？**

- 推理时 BN 是固定仿射变换（μ、σ、γ、β 为常数）；
- 可把缩放折叠进 W、偏移折叠进 b，数学上完全等价；
- 免一次访存 + 一个 kernel，零精度损失。

**Q4：算子融合为什么能加速？**

- 减少中间结果写回/读取（访存受限算子收益最大）；
- 减少 kernel 启动开销（小算子多时明显）；
- 融合后可整体做更优调度（寄存器复用）。

**Q5：NHWC 和 NCHW 怎么选？**

- NHWC 空间连续，SIMD 向量化友好，GPU/ARM + INT8 常更快；
- NCHW 逐通道处理自然，某些算子/框架默认；
- 全局看：布局转换有成本，交给引擎做布局传播最优。

**Q6：pin memory 为什么能加速 CPU->GPU 拷贝？**

- 锁页内存可被 GPU DMA 直接访问，省去先拷到临时锁页区的步骤；
- 配合 non_blocking 实现异步拷贝；
- 常用于 DataLoader。

**Q7：kernel launch 开销是什么？怎么减少？**

- 每次 kernel 启动有几微秒 CPU 侧开销；
- 轻量网络小算子多，launch 开销占比高；
- 减少：算子融合、CUDA Graph（整图一次提交）。

**Q8：CUDA stream 的作用？**

- 提供并行执行通道：stream 间可并发，stream 内串行；
- 用于多路并发推理、计算与拷贝重叠；
- GPU 已饱和时多 stream 无收益。

**Q9：动态 batching 的原理与代价？**

- 在时间窗内攒请求组成大 batch，摊薄权重加载，提高吞吐；
- 代价：排队延迟增加；
- 需要配置 max queue size / delay 上限。

**Q10：模型 FLOPs 低但实际慢，可能的原因？**

- 访存受限（算术强度低，如逐元素算子、1×1）；
- 算子碎片化，launch 开销大；
- 框架实现差（无融合、布局转换多）；
- 预处理/后处理在 CPU 拖慢端到端；
- 用 nsys/ncu 定位真实瓶颈。

**Q11：如何定位推理热点？**

- nsys 看整体时间线（CPU/GPU 是否重叠、拷贝占比）；
- ncu 看单 kernel（带宽、occupancy）；
- PyTorch Profiler 定位算子级耗时；
- trtexec 看逐层耗时。

**Q12：cudnn.benchmark=True 什么时候用？**

- 输入尺寸固定时开启，首次自动搜索最优卷积算法；
- 尺寸多变时每次重搜，反而变慢（此时用默认 False）。

**Q13：CV 推理优化和 LLM 推理优化的异同？**

- 同：融合、量化、图优化、batch；
- 异：LLM 是自回归 + KV Cache 管理（PagedAttention、连续批处理）；CV 是变分辨率、预处理流水线、NMS 后处理；
- 见 [llm_interview_note/06.推理](../../llm_interview_note/06.推理/)。

## 9.总结

- **先测后优**：nsys/ncu 定位是计算、访存还是调度瓶颈；
- **算子融合**是第一收益来源（Conv+BN+ReLU、推理期 BN 免费化）；
- **访存常是瓶颈**：布局（NHWC）、内存池、zero-copy、pin memory；
- **图优化**编译期完成：常量折叠、死代码消除、布局传播；
- **并行调度**：CUDA stream、动态 batching、预处理流水线；
- **低精度**（FP16/INT8）是最后的大招，衔接 [2.模型压缩](../2.模型压缩/2.模型压缩.md) 与 [4.部署框架](../4.部署框架/4.部署框架.md)。
