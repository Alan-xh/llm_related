# 3. 音乐生成模型

## 1. 概述

音乐生成（AI Music Generation）是音频生成中**结构最复杂**的任务：一首 3 分钟的流行曲包含多轨乐器、和弦进行、小节/乐段层级结构，要求**长程一致性**（副歌重复、调性统一）与**高音质**同时成立。其技术路线经历了三个时代：

1. **符号时代（2017~2020）**：生成 MIDI/钢琴卷帘（piano roll），代表为 MusicTransformer；
2. **波形大规模时代（2020~2022）**：Jukebox 用 VQ-VAE + 稀疏 Transformer 直接生成原始音乐波形，首次证明端到端可行；
3. **Token/Latent 大模型时代（2023~）**：MusicLM（AudioLM 范式 + 文本对齐）、MusicGen（EnCodec + 单阶段 LM，开源事实标准）、Stable Audio（latent diffusion）、Suno/Udio（产品级一体化架构）。

```
音乐生成技术演进:

MIDI 符号生成          波形离散 Token          条件大模型 / Latent
(MusicTransformer) ──> (Jukebox, VQ-VAE) ──> (MusicLM / MusicGen / Stable Audio / Suno)
     1990s-2020            2020-2022               2023-now
     结构好, 音色差         音色好, 结构弱            结构+音色+可控性平衡

```

---

## 2. 符号（MIDI）路线：MusicTransformer

### 2.1 建模方式

MusicTransformer（Google, 2018）把 MIDI 事件表示为事件序列（note-on / note-off / time-shift / velocity 的词表，大小约 300+），用 Transformer 自回归生成。其核心贡献是 **Relative Position Attention（相对位置注意力）**：

$$\text{Attn}(q, k)_{i,j} \propto \exp\!\Big( \frac{q_i^\top (k_j + w_{j-i})}{\sqrt{d}} \Big)$$

把绝对位置 embedding 换成相对距离可学习偏置 $w_{j-i}$，配合 **MIDI-like / AD / ARAD** 三种事件表示，使模型能捕捉音乐中跨越数百事件的**远距离重复结构**（如主题再现、回旋曲式），长度外推能力显著强于绝对位置编码。

### 2.2 符号路线的优缺点

* **优点**：序列短（每秒仅数个事件）、结构可控（可直接指定和弦/调式/节拍）、可编辑、可由 MIDI 合成器免算力回放；
* **缺点**：**丢失音色与混音信息**（MIDI 只记录"演奏指令"不记录音色采样），表现力受限于合成器；真实音乐里人声、吉他滑音、电子音色等无法精确符号化。

后续工作：PopMag / PopMusic Transformer（和弦与小节感知）、Remi（小节/节拍 token 化）、图/结构化先验（先规划和弦进行再填旋律的两阶段方法）。

## 3. Jukebox：波形级 VQ-VAE 生成

OpenAI Jukebox（2020）是首个高保真歌曲生成系统（含人声），三层层级 VQ-VAE + 稀疏 Transformer：

```
Jukebox 三层架构 (自底向上压缩, 自顶向下生成):

原始波形 (44.1kHz 立体声)
   │
   ▼ [VQ-VAE bottom]  ~ 码率最高: 还原音色细节      (codebook 2048, 8192bps 级)
   ▼ [VQ-VAE middle]  中间层
   ▼ [VQ-VAE top   ]  ~ 码率最低: 保留旋律/和声结构   (codebook 64, 压缩 ~8x/层)
   │
生成: [Upsampler Level-5 LM] --> top codes
      [Prior Level-4/3 LM]  --> middle/bottom codes  (以 top codes 与歌词/艺人条件)
      [Decoder]             --> 波形

```

* **层级 VQ**：三层 VQ-VAE 逐层压缩（每层 ~8 倍时间压缩率），top 层 1 秒音频仅几十个 code，LM 在这层建模长程音乐结构；
* **条件**：艺人/流派 embedding + **歌词**（字符级，与音频对齐）；
* **代价**：5B 参数 + 数百 GPU/天训练；生成 1 分钟音频需 **数小时采样**（自回归逐 code + 上采样），完全无法产品化；音乐性评价--长程和声一致性仍有限，"结构漂移"明显。

> **面试定位**：Jukebox 证明了"波形端到端"可行但算力上不可行，直接推动了后续"codec + 轻量 LM"（MusicGen）与"latent diffusion"（Stable Audio）两条更高效的路线。

## 4. MusicLM：文本条件的三阶段生成

MusicLM（Google, 2023）= AudioLM 三阶段 + MuLan 文本-音频对齐：

* **Semantic 层**：用 MuLan 音乐表征 K-means 得 semantic tokens（捕捉旋律/和声内容）；
* **Acoustic 层**：SoundStream RVQ tokens（捕捉乐器音色、混音）；
* **生成**：文本经 MuLan 文本塔得到 embedding 作为 semantic LM 前缀条件，后续 coarse/fine acoustic 阶段照搬 AudioLM；
* **能力**：文本到音乐、旋律迁移（哼唱旋律 + 风格文本）、长片段（minutes 级，滑窗拼接）；
* **局限**：多阶段级联推理极慢，未开源。

---

## 5. MusicGen：Codec + 单阶段 LM（开源事实标准）

MusicGen（Meta, 2023）把 AudioLM 式层级简化为**单阶段**，成为开源音乐生成的标准基线：

| 组件 | 设计 |
| --- | --- |
| **Codec** | EnCodec 32 kHz mono，50 Hz 帧率，4 层 RVQ codebook（$K=2048$） |
| **LM** | Decoder-only Transformer（300M / 1.5B / 3.3B），词表 = 2048 + 特殊 token |
| **多 codebook 因果化** | **Delay pattern**：第 $k$ 层 codebook 延迟 $k$ 步，使 4 层 token 展平后仍可用标准 next-token prediction |
| **文本条件** | T5/FLAN-T5（或 MERT）encoder + **cross-attention** 注入每层 |
| **引导** | **CFG**：训练时 10% 丢弃文本条件，推理时 $\epsilon_\theta^{\text{cfg}} = \epsilon_\theta(x_t, c) + w \cdot (\epsilon_\theta(x_t, c) - \epsilon_\theta(x_t, \varnothing))$ 类似的 logit 外推 |
| **结构控制** | 无显式小节模型，长程一致性靠数据与规模（30 秒训练窗） |

```
MusicGen 推理流水线:

文本 ──> [T5 Encoder] ──> cross-attn 条件 ──> [Transformer LM + Delay Pattern]
                                                │ 自回归 (top-k / CFG)
哼唱旋律 ──> [Chroma 提取] ──> melody 条件 ──────┘
                                                ▼
                        EnCodec token 序列 [4 层 x T] ──> [EnCodec Decoder] ──> 32kHz 音乐

```

**工程数据量级**：1.5B 模型 30 秒音频约 1500 帧位置 $\times$ 4 codebook = 6000 token；A100 生成约 20~40 秒；参数效率上 MusicGen 以 1/10 参数超越 MusicLM 人评。

## 6. Stable Audio：音乐/音效的 Latent Diffusion 路线

与 MusicGen 的离散 AR 路线平行，Stable Audio（Stability AI, 2023）走**连续 latent diffusion**：

* **Codec**：CRESCENDO/VAE，41 Hz latent 帧率，支持 44.1 kHz **立体声**（这是相对 MusicGen 的显著优势），时间压缩约 1024 倍；
* **Diffusion**：U-Net（1.5B），cross-attention 注入 CLAP 文本 embedding 与**时间条件**（起始/时长秒数，可生成指定长度、最长 47 秒训练窗）；
* **采样**：DPM-Solver ++，100 步（后续版本 4~20 步）；
* **Stable Audio 2.0（2024）**：升级 DiT backbone + licensed 数据 + audio-to-audio 编辑/延展，最长 3 分钟。

## 7. Suno 类产品架构剖析

Suno / Udio（2024）代表**产品级一体化音乐生成**。虽然闭源，从专利、博客与社区逆向可归纳出典型架构：

```
Suno 类产品推断架构 (工业级 text-to-song 全链路):

用户输入: [风格描述 + 歌词 (可自动生成)] 
    │
    ▼ [1] LLM 歌词/结构规划: 生成带结构标签的词
    │        [Intro] [Verse 1] [Chorus] [Bridge] ... 每段附 style prompt
    ▼ [2] 音频生成主干 (推测为 AR codec LM 或 latent diffusion, ~分钟级上下文)
    │        条件 = 风格文本 embedding + 歌词 + 段落结构 token
    ▼ [3] 人声与伴奏联合建模 (统一 token 流, 含唱词对齐信息)
    ▼ [4] 后处理: 响度归一 / 母带 (mastering) / 分轨 (stems) / 延展 (extend)
    ▼
成品歌曲 (2~4 分钟, 44.1kHz 立体声)

```

关键工程要点：

1. **歌词-音频对齐**：人声需要逐字对齐旋律，类似可唱 TTS（singable TTS）；工业上通常在 token 层混合歌词 token 与音频 token，或单独人声轨 + 伴奏轨再混合；
2. **长结构**：滑窗自回归 + 段落 embedding 保持"副歌再现"；Udio 的 extend/inpainting 支持交互式续写（类似图像 outpainting 的音频版）；
3. **版权与数据**：这是产品级音乐模型最大的非技术风险（Suno/Udio 均面临唱片业诉讼），自建授权曲库或合成数据增强是核心壁垒。

## 8. 长结构一致性：小节与和弦结构建模

音乐的多尺度层级结构（拍 -> 小节 -> 乐句 -> 乐段 -> 整曲）对生成模型是核心挑战。主要方案：

### 8.1 结构先验注入

* **和弦/调式条件**：将和弦进行（chord progression）作为额外条件序列（cross-attention），如 PopMag、JamGPT 类工作；
* **小节感知 token 化**：REMI 把 Bar/Beat/Chord 显式编为 token，LM 显式"数拍子"，避免节奏漂移；
* **两阶段规划**：先由小模型/规则生成曲式（verse-chorus 布局）与和弦骨架，再以此为条件生成音频 token（计划-执行范式）。

### 8.2 注意力与位置编码层面

* **长上下文**：分钟级音乐 = 数万 token，需要 RoPE 长度外推 / 线性注意力 / 分层记忆（Jukebox 用 top-level code 压缩上下文本质也是此思路）；
* **结构重复偏置**：音乐大量存在精确重复（副歌），相对位置注意力与 n-gram 复制先验有助捕捉。

### 8.3 实测现象（面试可引用）

* 纯 waveform 模型在 30 秒训练窗外**调性漂移**明显（Jukebox 论文观察到 key drift）；
* MusicGen 类模型生成超过训练窗长度时节奏逐渐加快/变慢；
- 滑窗 + overlap-add 或 chunk 条件前缀（把上一段尾部 code 作为下一段 prompt）是工业界最常用的长音频方案。

## 9. Symbolic（MIDI）vs. Waveform 路线对比

| 维度 | Symbolic（MIDI / piano roll） | Waveform / Codec token |
| --- | --- | --- |
| **表示** | 离散演奏事件（音高/时值/力度） | 波形或 RVQ/latent 连续/离散表示 |
| **序列长度** | 极短（每秒个位数事件） | 长（50~600 token/s 或高维 latent） |
| **音色/混音** | 无（依赖音色库） | 完整保留 |
| **人声** | 无法表示 | 可生成 |
| **结构可控性** | 强（显式和弦/小节操作） | 弱（隐式学习，需额外条件） |
| **可编辑性** | 极强（改一个音） | 弱（需 inpainting/region 操作） |
| **算力需求** | 低（CPU 可跑） | 高（GPU 集群训练） |
| **代表** | MusicTransformer、REMI 系、AIVA | Jukebox、MusicLM、MusicGen、Stable Audio |
| **适用场景** | 编曲辅助、BGM 骨架、音乐教育 | 成曲生成、配乐、产品级 demo |

> **融合趋势**：Symbolic 先规划结构与和声，再由 waveform 模型实现音色（如 Meta 的芝麻街系工作、商业产品普遍的"两阶段"设计），鱼与熊掌兼得。

## 10. PyTorch 代码实战：带小节感知的音乐 Token 化（简化 REMI）

```python
import torch
import torch.nn as nn

# ------------------------------------------------------------
# 简化版 REMI 风格 token 化: Bar -> Beat -> Position -> Pitch -> Duration
# ------------------------------------------------------------
SPECIALS = ["<bos>", "<eos>", "<pad>"]
BAR = "<bar>"; BEATS = [f"<beat_{i}>" for i in range(4)]     # 4/4 拍
PITCHES = [f"<pitch_{p}>" for p in range(21, 109)]           # MIDI 钢琴音域
DURATIONS = [f"<dur_{d}>" for d in [0.25, 0.5, 1.0, 2.0]]   # 拍长

VOCAB = SPECIALS + [BAR] + BEATS + PITCHES + DURATIONS
tok2id = {t: i for i, t in enumerate(VOCAB)}


def note_events_to_remi(events, beats_per_bar=4):
    """
    events: [(start_beat, pitch, dur_beat), ...] 已按 start 排序
    展示如何插入显式小节/节拍结构 token
    """
    tokens = ["<bos>"]
    cur_bar = -1
    for start, pitch, dur in events:
        bar = int(start // beats_per_bar)
        if bar != cur_bar:
            tokens.append(BAR)                 # 新小节 -> 显式 "数拍子"
            cur_bar = bar
        tokens.append(BEATS[int(start) % beats_per_bar])     # 小节内节拍
        tokens.append(f"<pitch_{pitch}>")
        tokens.append(f"<dur_{dur}>")
    tokens.append("<eos>")
    return torch.tensor([tok2id[t] for t in tokens], dtype=torch.long)


class MusicTransformer(nn.Module):
    """小节感知自回归音乐 LM (演示核心结构)"""

    def __init__(self, vocab_size=len(VOCAB), d_model=512, n_layers=8, n_heads=8):
        super().__init__()
        self.tok_embed = nn.Embedding(vocab_size, d_model)
        self.pos_embed = nn.Embedding(4096, d_model)   # 实际建议换 RoPE
        self.blocks = nn.TransformerDecoder(
            nn.TransformerEncoderLayer(d_model, n_heads, dim_feedforward=4 * d_model,
                                       batch_first=True),
            num_layers=n_layers,
        ) if False else nn.TransformerEncoder(
            nn.TransformerEncoderLayer(d_model, n_heads, dim_feedforward=4 * d_model,
                                       dropout=0.1, batch_first=True),
            num_layers=n_layers,
        )
        self.head = nn.Linear(d_model, vocab_size)

    def forward(self, tokens: torch.Tensor):
        """tokens: [B, L] -> logits [B, L, V]"""
        L = tokens.size(1)
        h = self.tok_embed(tokens) + self.pos_embed.weight[:L]
        # 因果 mask 保证自回归性
        causal = torch.triu(torch.ones(L, L, device=tokens.device), diagonal=1).bool()
        h = self.blocks(h, mask=causal)
        return self.head(h)


@torch.no_grad()
def generate(model, prompt: torch.Tensor, steps: int = 512, top_k: int = 50):
    """top-k 自回归续写 (MIDI 事件流)"""
    model.eval()
    tokens = prompt.clone()
    for _ in range(steps):
        logits = model(tokens[:, -1024:])          # 上下文窗口截断
        probs = torch.softmax(logits[:, -1] / 1.0, dim=-1)
        topv, topi = probs.topk(top_k, dim=-1)     # top-k 采样
        nxt = topi.gather(-1, torch.multinomial(topv, 1))
        tokens = torch.cat([tokens, nxt], dim=1)
        if (nxt == tok2id["<eos>"]).all():
            break
    return tokens


if __name__ == "__main__":
    # 模拟一段 C 大调琶音事件: (起始拍, MIDI 音高, 时值拍)
    events = [(0.0, 60, 0.5), (0.5, 64, 0.5), (1.0, 67, 0.5), (1.5, 72, 0.5),
              (4.0, 62, 1.0), (5.0, 65, 1.0)]
    seq = note_events_to_remi(events)
    print(f"REMI tokens: {seq.tolist()}  (vocab={len(VOCAB)})")

    model = MusicTransformer()
    logits = model(seq.unsqueeze(0))
    print(f"LM logits: {tuple(logits.shape)}")

    out = generate(model, seq.unsqueeze(0), steps=64)
    print(f"Generated {out.size(1) - seq.size(0)} new event tokens")
```

## 11. 总结与最佳实践

* **路线选择**：要结构可控、可编辑、低算力 -> symbolic（MIDI）；要成品音质、人声 -> waveform（codec LM 或 latent diffusion）；产品级系统普遍**两阶段融合**（结构规划 + 波形实现）。
* **长结构一致性**是音乐生成区别于音效/语音生成的核心难题：显式方案（和弦/小节 token、曲式规划器）与隐式方案（长上下文、层级压缩、滑窗拼接）互补使用。
* **工业选型参考**：开源自部署首选 MusicGen（生态成熟、可控性好）或 Stable Audio Open（短音效/采样）；需要人声成曲则接近 Suno 式全链路（歌词规划 + 唱词对齐 + 母带），工程量与数据壁垒都显著更高。
* **评估**：音乐生成尚无公认的自动指标体系，实务中人评（MOS/偏好对拍）+ FAD + 音乐理论检查（调性/节拍稳定性）组合使用。
