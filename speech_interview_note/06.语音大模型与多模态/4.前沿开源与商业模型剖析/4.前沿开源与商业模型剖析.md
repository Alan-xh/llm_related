# 4. 前沿开源与商业模型剖析

## 1. 概述

2023~2025 年，语音大模型从「ASR + LLM 拼接」快速演进到「单模型实时语音对话」。本章对**最具代表性的开源与商业模型**逐一剖析架构，并给出横向对比大表。选样的覆盖面刻意拉开：

* **商业闭源**：GPT-4o Realtime（OpenAI）、Gemini Live（Google）
* **开源全双工**：Moshi（Kyutai）
* **开源多模态 LLM**：Qwen2-Audio / Qwen2.5-Omni（阿里）、MiniCPM-o（面壁）
* **开源专项**：SenseVoice（ASR）、CosyVoice 2（TTS）、GLM-4-Voice（智谱）

## 3. 商业闭源模型

### 3.1 GPT-4o Realtime（OpenAI）

* **定位**：单神经网络处理文本/视觉/音频输入输出的原生多模态（"omni"），Realtime API 面向全双工语音对话。
* **架构（公开信息推断 + 技术报告）**：端到端训练的单模型，语音直接进多模态 Transformer，输出直接为音频 token；无独立 ASR/TTS 模块。
* **关键数字**：语音对话平均延迟 **320ms**（最短 232ms），对比 GPT-4 级联方案的 ~5.4s，快一个数量级。
* **交互机制**：API 提供会话（session）级管理，支持**服务端 VAD 检测打断**（用户插话自动截断模型音频）与 `response.cancel` 主动取消；本质仍是「快速轮换 + 原生低延迟」，barge-in 由 server VAD + 语义判断联合完成。
* **面试要点**：延迟数字、为何原生比级联快（无 VAD 等待、无三模块串行）、副语言信息保留（能听出情绪并带情绪回应）。

### 3.2 Gemini Live（Google）

* **定位**：Google 助理级的实时多模态对话，依托 Gemini 系列原生多模态（natively multimodal）预训练路线：从预训练起文本/音频/视频就混合训练，而非后置 adapter 对齐。
* **架构特点**：Gemini 1.5/2.x 把音频作为原生输入模态（音频 token 直接进 Transformer），输出侧配合 TTS；Live 模式支持打断、扩展上下文（记忆窗口长是差异化卖点）。
* **对比 GPT-4o**：Gemini 强调**长上下文 + 多模态原生预训练**（非 post-hoc alignment），Live API 同样提供 barge-in 与实时流式；细节未完全公开，面试以路线对比为主。

## 4. 开源全双工模型：Moshi（Kyutai）

Moshi 是首个公开架构的全双工实时语音对话模型（2024），其设计已在第 3 篇详解，此处聚焦架构事实：

```
 用户音频(24kHz) ──> [Mimi Codec] ──> 12.5Hz x (1语义码本 + 11声学码本)
                                          │
        ┌─────────────────────────────────┴──────────────────────────┐
        ▼ 双流 time-synchronous Transformer (7B, 12.5Hz 步进)          ▼
 用户流(client): 语义+声学并行输入                    模型流(model): Inner Monologue
                                                              │
                          [Mimi Decoder] <── 声学码 ──────────┘
                              │
                              ▼
                       24kHz 模型语音输出
```

* **双流**：用户流与模型流共享同一 12.5Hz 时间轴，模型每步既「听」又「说」。
* **Inner Monologue**：模型流以文本 token 作为语义轨，声学码条件于文本轨生成，抑制语义漂移。
* **延迟**：理论可达 ~160~200ms（12.5Hz 帧率 x2 帧理论下限 + 解码），实测对话延迟 200ms 级。
* **Tokenizer**：Mimi codec，语义蒸馏（DistilHuBERT）+ RVQ，**同时输出语义与声学信息**，是全双工架构的 codec 关键创新。
* **开源**：模型权重与代码全开放，是学术界研究全双工的事实基线。

## 5. 开源多模态 LLM

### 5.1 Qwen2-Audio / Qwen2.5-Omni（阿里）

**Qwen2-Audio（语音理解型）**：

* Whisper Encoder 初始化 + **继续大规模多任务预训练**（对齐阶段即混入 30+ 任务：ASR/S2TT/SER/语音 chat/音频事件）。
* Connector 为简单 Linear 降采样（4 帧拼 1），token 率 ~12.5/s。
* 两阶段训练：多任务对齐预训练 -> SFT 指令微调（chat 格式，任务混合采样）。
* 卖点：无需 text prompt 的「语音 chat」交互、跨任务指令泛化。

**Qwen2.5-Omni（End-to-end 多模态，2025.3）**：

* 单一模型统一文本/图像/音频/视频输入与**文本+语音同步输出（TTSR: Text and Speech Generation in parallel）**。
* 核心架构：**Thinker-Talker 双子系统**--Thinker 为 LLM 主干负责理解与生成文本 token；Talker 为轻量 Transformer，**并行**消费 Thinker 隐状态流式输出语音 token（不逐 token 串行等待）。
* 音频输入用 Whisper 式 encoder + Conv 降采样；语音输出用其自研 codec token。
* 半双工（播报时暂停理解用户插话需靠前端打断），但延迟进入数百 ms 级。
* 面试要点：Thinker-Talker 分离思想（理解与发声解耦、Talker 流式并行）、与 Moshi 双流的区别（生成并行 vs 交互全双工）。

### 5.2 MiniCPM-o（面壁智能）

* 端侧多模态模型系列，MiniCPM-o 2.6 集成「视觉 + 音频」实时交互，目标为**手机/车载端侧部署**。
* 架构：多模块组成（ViT 视觉 + Whisper 式音频 encoder + LLM + 语音 decoder），模块化「o」架构，音频输入经 conv 降采样进 LLM，输出接流式 TTS 头。
* 面试要点：端云协同（端侧推理 + 低延迟 codec）、多模态联合对齐训练（视觉-音频-文本三模态 instruction tuning）。

## 6. 开源专项模型

### 6.1 SenseVoice（阿里，语音理解/ASR）

* 定位：高精度**多语种 ASR + 情感识别（SER）+ 声学事件检测（AED）**三合一理解模型，非 LLM。
* 架构：**非自回归**（类似 CTC/conditional encoder-decoder 无自回归解码），一次前向出全部结果，推理速度数倍于 Whisper（官方报告推理耗时约为 Whisper-large 的 ~1/15，遵循非流式离线场景）。
* 训练：30 万小时级多语种（中/粤/英/日/韩）+ 情感 + 事件标注，输出格式用特殊 token 标记（`<|HAPPY|>` `<|APPROXIMATE|>` 等）。
* 面试要点：为什么非自回归快（无逐 token 解码）、情感/事件如何统一进 token 输出格式、与 Whisper 的流式差异（SenseVoice 离线、Whisper 可流式改造）。

### 6.2 CosyVoice 2（阿里，零样本 TTS）

* 定位：流式零样本 TTS，继承 CosyVoice 的「**语义 token (SSM: speech semantic model, HuBERT 系) -> codec token**」两级方案。
* 架构改进：统一流式与非流式生成（有限状态解码）；**token 复流输入的 LLM（Qwen 系初始化）+ Flow Matching 解码器**；零样本克隆延迟低至 **150ms 首包**。
* 面试要点：语义 token + 声学 token 分工（内容 vs 音质）、Flow Matching vs Diffusion vocoder、指令控制（instruct TTS：用文本描述说话风格）。

### 6.3 GLM-4-Voice（智谱，端到端语音对话）

* 定位：端到端**语音进语音出**对话模型，价值在于直接情感理解与情感语音回应（带情绪/语速/风格的 direct speech-to-speech）。
* 架构：**GLM-4 文本 LLM + Speech Tokenizer（语义 token，Whisper Encoder + RVQ 量化）+ Speech Decoder**。
* 训练三阶段：模态对齐（语音理解）-> 语音生成对齐（解码器学说话）-> 语音-语音对话集成（直接 audio in audio out 微调）。
* 面试要点：情感在语音 token 中如何保留（encoder 侧用非纯 ASR 目标训练）、语音输出 token 码率控制、与级联方案的情感保真对比。

### 7.1 架构选择的关键分野

**分野一：语音 token 表示**

| 路线 | 代表 | 权衡 |
| --- | --- | --- |
| 语义 token（SSL 聚类 / 蒸馏） | SpeechGPT、CosyVoice 前级、GLM-4-Voice | LLM 易建模、内容稳；音色细节丢失，需声学 decoder 补 |
| 声学 codec token（RVQ 多码本） | VALL-E、Moshi（Mimi） | 高保真可直接重建；码率高，需并行码本/分层建模 |
| 语义+声学混合 | Mimi（1 语义蒸馏 + 11 声学）、CosyVoice 两级 | 兼顾，工业主流 |

**分野二：encoder 类型**

| 路线 | 代表 | 权衡 |
| --- | --- | --- |
| ASR 弱监督 encoder | Whisper（Qwen 系、MiniCPM-o） | 语义强、多语种；副语言弱 |
| 自监督 encoder | HuBERT / w2v-BERT（GLM-4-Voice tokenizer 前身、SALMONN 双流之一） | 无标注可扩展、声学细节好 |
| 多编码器互补 | SALMONN（Whisper + BEATs） | 覆盖语义 + 事件/情感 |

**分野三：全双工方案**

| 路线 | 代表 | 权衡 |
| --- | --- | --- |
| 前端打断（VAD/AEC 强杀） | 级联、半双工 Speech-LLM | 工程可控；打断生硬、无 backchannel |
| 服务端 VAD + 快速轮换 | GPT-4o Realtime | 接近全双工体验、稳定可控 |
| 双流 time-synchronous | Moshi | 真全双工；训练数据难、易自言自语 |
| 生成并行（Thinker-Talker） | Qwen2.5-Omni | 降低输出延迟至流式，交互仍半双工 |

| 模型 | 音频训练数据 | 参数量 | 训练范式要点 |

## 8. 工程视角：怎么选型

| 场景 | 推荐方案 | 理由 |
| --- | --- | --- |
| 离线高精度转写/理解 | Whisper-large / SenseVoice | 成熟、精度高、SenseVoice 附带情感事件 |

| 低延迟情感语音对话 | GPT-4o Realtime / GLM-4-Voice / Qwen2.5-Omni | 副语言保真、亚秒响应 |

| 端侧/车载 | MiniCPM-o、SenseVoice-small | 端侧算力友好 |

## 9. PyTorch 示例：统一视角下的接口抽象

```python
from dataclasses import dataclass
from typing import Optional

@dataclass
class SpeechLLMConfig:
    name: str
    input_token: str          # "embedding" (连续) / "semantic" / "codec"
    output_token: Optional[str]  # None(纯理解) / "semantic" / "codec"
    duplex: str               # "half" / "server_vad" / "full"
    frame_rate_hz: float      # 语音 token 帧率

MODELS = {
    "gpt4o_realtime": SpeechLLMConfig("GPT-4o", "embedding", "codec",
                                      "server_vad", 12.5),
    "moshi":          SpeechLLMConfig("Moshi", "codec", "codec",
                                      "full", 12.5),
    "qwen2_audio":    SpeechLLMConfig("Qwen2-Audio", "embedding", None,
                                      "half", 12.5),
    "glm4_voice":     SpeechLLMConfig("GLM-4-Voice", "semantic", "semantic",
                                      "half", 25.0),
    "cosyvoice2":     SpeechLLMConfig("CosyVoice2", "semantic", "codec",
                                      "half", 25.0),
}

def estimate_first_packet_latency(cfg: SpeechLLMConfig,
                                  vad_ms=0, llm_first_ms=250,
                                  codec_ms=100, net_ms=80) -> float:
    """粗略估算首响延迟 (ms): 全双工无 VAD 等待, 半双工需端点检测"""
    endpoint = 0 if cfg.duplex in ("full", "server_vad") else 600
    return endpoint + llm_first_ms + codec_ms + net_ms

for name, cfg in MODELS.items():
    if cfg.output_token:  # 仅对话型模型
        print(f"{name:16s} ~{estimate_first_packet_latency(cfg):.0f} ms")
# 输出示意: gpt4o_realtime ~430ms / moshi ~430ms /
#           glm4_voice ~1030ms / cosyvoice2 ~1030ms (仅TTS链路)
```

## 10. 总结与最佳实践

* **两条主线**：商业闭源（GPT-4o / Gemini Live）以原生多模态 + 服务端 VAD 快速轮换做到 300ms 级体验；开源阵营以 Moshi（双流全双工）、Qwen2.5-Omni（Thinker-Talker 流式生成）、GLM-4-Voice（端到端情感对话）从不同切角逼近。
* **token 表示是架构第一决策**：语义 token 利内容、codec token 利音质、混合（Mimi、CosyVoice 两级）是工业主流。
* **全双工三个实现层级**：前端强杀（级联）-> 服务端 VAD 轮换（GPT-4o）-> 双流同步（Moshi），成本与自然度依次递增。
* **面试答题框架**：拿到任何一个新模型，先问四个问题--encoder 是什么、connector/帧率多少、输出 token 类型、全双工怎么做，即可完整复原其架构定位。
