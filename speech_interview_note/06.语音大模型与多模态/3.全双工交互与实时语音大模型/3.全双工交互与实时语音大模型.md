# 3. 全双工交互与实时语音大模型

## 1. 概述

人类对话是**全双工（Full-Duplex）**的：我们边听边说、随时打断对方、用「嗯」「对」做 backchannel（附和）、在对方迟疑时抢话。而传统语音助手（级联 ASR+LLM+TTS）是**半双工状态机**：必须等 VAD 判定用户说完 -> LLM 生成 -> TTS 播报 -> 再开放麦克风，全程「你说我听」轮流进行。

实时语音大模型（Realtime Speech-LLM）的目标是把交互从状态机升级为**连续同步流（continuous time-synchronous stream）**：

```
 半双工状态机 (轮次制):
 用户 ──说话──> [静音检测] ──> LLM ──> TTS ──> 播报 ──> (禁止打断) ──> 等用户...

 全双工连续流 (time-synchronous):
 用户 ═══连续音频流═══> ┌─────────────────┐
                       │  Speech-LLM      │ ═══连续音频流═══> 用户
                       │ (同时听 + 同时说)  │
                       └─────────────────┘
   特性: 可随时打断(barge-in) / 附和(backchannel) / 自然抢话 / 零轮次等待
```

这一篇覆盖全双工的核心机制：turn-taking 轮次检测、barge-in 打断、双流架构（Moshi 的 Inner Monologue）、延迟预算分解与实时性指标。这是 2024 年后语音岗面试的最热考点。

---

## 2. 全双工的定义与核心能力

### 2.1 全双工的四个关键能力

| 能力 | 定义 | 半双工系统表现 |
| --- | --- | --- |
| **同时听与说** | 模型播报语音的同时持续接收并理解用户音频 | 播报期间麦克风关闭或输入被丢弃 |
| **Barge-in 打断** | 用户随时插话，模型立即停止播报并响应 | 必须等播报完 / 靠前端 VAD 强杀 TTS |
| **Turn-taking 轮转** | 预测「该谁说了」，自然交接话轮 | 依赖固定静音阈值（如 800ms），遇停顿误抢答 |
| **Backchannel 附和** | 听的时候发出「嗯」「对」「嗯哼」等非抢话反馈 | 完全没有，交互机械 |

### 2.2 全双工的难点

1. **自回归模型的根本矛盾**：LLM 解码生成 token $t+1$ 时只能条件于 $\le t$ 的信息，而全双工要求「说」的每一步都实时条件于正在到来的用户音频流。
2. **训练数据缺失**：对话数据几乎都是轮次制的（一条说完再一条），缺少「重叠语音 + 打断时刻 + 双方并行」的时间同步标注。
3. **工程实时性**：编解码、模型前向、流式合成全部要在音频实时率（real-time factor, RTF < 1）内完成。

---

## 3. Turn-Taking 轮次检测

### 3.1 问题定义

给定连续用户音频流，预测语义完整点（semantic completeness）与话轮交接点（turn-shift），决定「何时开始回应」。形式化为预测用户在时刻 $t$ 后 $\Delta$ 内是否会停止说话：

$$P_{\text{shift}}(t) = P\big(\text{user stops within } (t, t+\Delta]\ \mid\ \text{audio}_{\le t},\ \text{dialogue context}\big)$$

### 3.2 方案对比

| 方案 | 原理 | 延迟特性 | 缺点 |
| --- | --- | --- | --- |
| **固定 VAD 静音阈值** | 静音超 500~800ms 判句尾 | 恒定偏大 | 停顿即误抢答；语速自适应差 |
| **统计 turn-taking 模型**（如 VAP / TurnGPT） | 在对话语料上学预测换话轮概率 | 可提前预测（anticipatory） | 需要时间同步对话标注 |
| **Speech-LLM 内生决策** | 模型自己输出「说话 token」或「倾听 token」，由生成行为隐式决定轮转 | 与推理同拍，零额外延迟 | 需要全双工训练数据 |

**VAP（Voice Activity Projection）** 类模型值得注意：它逐 100ms 预测未来双方的话音活动，包括「对方将在 500ms 内停止」的事件，可实现**预测式接话**--在用户完全停止前就开始生成回应，把感知延迟降为负数。

### 3.3 实用混合策略（工业界常见）

```
用户音频流 ──> [流式 VAD/能量] ──> 快速粗判(静音>200ms)
                    │
                    ▼
             [LLM 语义完整性打分] ──> 语义完整 + 静音 => 切换为"回应"状态
                    │                        │
                    └── 语义不完整(句中停顿) ──> 继续倾听等待
```

即：**VAD 给出候选切点，LLM 判断语义完整性**，两者都通过才响应，兼顾低延迟与不抢话。

## 4. Barge-in 打断机制

### 4.1 打断的两种实现层级

**层级一：前端打断（Pipeline 级，级联系统可用）**

```
 用户语音 ──> [AEC 回声消除] ──> [VAD 检测人声] ──> 打断信号 ──> kill TTS 播放
                                                          └──> 丢弃当前 LLM 生成
```

* **AEC（Acoustic Echo Cancellation）** 是前提：设备在播 TTS 时麦克风会拾到自己的声音，必须先回声消除再做 VAD，否则模型会「打断自己」。
* 端侧用 WebRTC AEC / Speex；智能音箱用专门的 AEC 芯片。
* 延迟：AEC+VAD 检测到人声约 **100~200ms**，加上杀 TTS，总打断响应 200~400ms。

**层级二：模型内生打断（End-to-End 级）**

全双工模型边说边听，当用户音频流条件注入后，模型自己决定停止生成语音 token 并转入倾听/回应。Moshi 的做法是把打断建模为时间同步流的一部分：用户插话 -> 语义冲突 -> 模型的多码本输出自然转向。这需要训练数据含打断样本（可用「对话 + 随机截断重叠」构造）。

### 4.2 打断的关键指标

* **打断响应延迟**：从用户开口到系统停止播报，工业要求 < 500ms（人感知自然阈值）。
* **误打断率（false barge-in）**：噪声、电视声、模型自己的声音引起误杀播报；AEC 残留回声是最常见根因。
* **打断后上下文保持**：被打断的话是否记入对话历史，回应是否能衔接被截断的内容。

## 5. 双流（Duplex）架构与 Moshi 的 Inner Monologue

### 5.1 双流 time-synchronous 架构

Moshi（Kyutai, 2024）是全双工 Speech-LLM 的标杆。核心设计：**两条并行的语义+声学 token 时间同步流，分别对应用户（"client"）与模型（"model"）**，共享同一个时间轴：

```
 时刻:            t1    t2    t3    t4    t5   ...
 用户流(client):  C1    C2    C3    C4    C5    <- 用户的语义token(由Mimi codec提取)
 用户声学码:      A1    A2    A3    A4    A5    <- 用户的声学token (并行码本)
 模型流(model):   M1    M2    M3    M4    M5    <- 模型自己"说"的语义token
 模型声学码:      B1    B2    B3    B4    B5    <- 模型输出的声学token (并行多码本)

 每个时间步 (12.5Hz): Transformer 同时接收 [C_t; A_t] 并自回归生成 [M_t; B_t]
 -> 同一模型、同一时间轴、真·边听边说
```

### 5.2 Inner Monologue：Moshi 的关键技巧

直接用声学 token 训练双流模型会导致「模型听不清自己/语义漂移」。Moshi 引入 **Inner Monologue（内心独白）**：模型流先用**文本 token** 作为前缀（语义轨道），声学码并行预测：

$$P(M_t, B_t \mid C_{\le t}, A_{\le t}, M_{<t}, B_{<t}) = P(M_t \mid \cdot) \cdot P(B_t \mid M_t, \cdot)$$

即**文本轨是声学轨的条件**。收益：

1. 文本轨锚定语义，模型「说的话」内容可控、幻觉更低；
2. 声学轨专注音色韵律，类似「先想后说」；
3. 消融实验显示加 inner monologue 后对话质量（内容一致性）显著提升。

### 5.3 Mimi Codec：全双工的 codec 基础

Moshi 配套的 **Mimi codec** 把 24kHz 音频压为 **12.5Hz 帧率**的 RVQ 码本（1 个语义蒸馏码本 + 11 个声学码本），用 DistilHuBERT 做语义蒸馏（semantic distillation）对齐语义空间。12.5Hz 是全双工的关键：**每个时间步 80ms**，模型每步既听又说，时间对齐自然成立。对比 EnCodec 75Hz，Mimi 直接把序列长度降 6 倍，使 time-synchronous 双流在算力上可行。

### 5.4 状态机 vs 连续流总结

| 维度 | 状态机（轮次制，含级联与多数 Speech-LLM） | 连续流（time-synchronous 双流） |
| --- | --- | --- |
| 代表 | GPT-4o realtime API（会话轮换式）、Qwen2.5-Omni（Thinker-Talker 半双工） | Moshi、全双工 SpeechLLM（dual-stream 类） |
| 麦克风状态 | 播报时关闭/忽略 | 永远开启，持续理解 |
| 打断 | 前端 AEC+VAD 强杀，或 API `cancel` 事件 | 模型内生，语义级自然打断 |
| Backchannel | 无 | 原生支持 |
| 实现难度 | 低，工程可控 | 高，需同步训练数据与双流解码 |
| 稳定性 | 高 | 易自言自语/抢话，需 RL/数据矫正 |

## 6. 延迟预算分解

### 6.1 端到端延迟公式

$$T_{\text{total}} = T_{\text{VAD/endpoint}} + T_{\text{ASR}} + T_{\text{LLM first token}} + T_{\text{TTS first chunk}} + T_{\text{network}}$$

### 6.2 级联 vs 端到端预算表（面试必背量级）

| 环节 | 级联系统 | 实时 Speech-LLM | 说明 |
| --- | --- | --- | --- |
| VAD / 端点检测 | 500~800ms（静音等待） | 0~100ms（流式内嵌） | 级联最大延迟源之一 |
| ASR 尾包结果 | 100~300ms（chunk 尾 + 重排序） | 0（无独立 ASR） | |
| LLM 首 token | 200~500ms（prefill + 首步解码） | 100~300ms（流式 prefill） | |
| TTS 首音频块 | 100~300ms（流式合成首 chunk） | 50~150ms（codec 解码首帧） | |
| 网络 RTT | 50~200ms | 50~200ms | WebSocket/WebRTC |
| **总计** | **~1.0s ~ 2.0s+** | **~300ms ~ 800ms** | GPT-4o：均值 320ms |

人类对话的自然话轮间隔（gap）约 **200~250ms**，超过 1s 即有「卡顿感」。因此：

* 级联系统的理论下限约 800ms~1s（VAD 等待占大头），**无法突破人类自然节奏**；
* 端到端实时模型才可能进入 500ms 内的「无缝对话」区间。

### 6.3 Delay 减半策略清单

1. **消灭 VAD 等待**：语义级 endpointing（LLM 判完整性）替代纯静音阈值，或预测式 turn-taking（VAP）。
2. **流式一切**：ASR 流式、LLM 流式 prefill（音频 chunk 到即算）、TTS 流式首 chunk 合成。
3. **Speculative / 边听边想**：用户说话期间 LLM 基于.partial 转写预生成候选，确认后秒回。
4. **KV-Cache 与状态保持**：会话级 cache 复用，多轮对话不重算历史音频 embedding。
5. **小 codec 帧率**：12.5Hz（Mimi）代替 75Hz（EnCodec），解码步数少 6 倍。
6. **算子级**：INT8/KV 量化、attention 算子融合、端云协同（端侧 codec + 云侧 LLM）。

## 7. 实时性指标

| 指标 | 定义 | 工业目标值 |
| --- | --- | --- |
| **TFRT（Time to First Response Token）** | 用户停止说话 -> 系统第一个响应音频到达 | < 500ms（对话级），< 800ms（可接受） |
| **首响延迟（First Audio Latency）** | 同上但计至首个可听音频 | 同 TFRT |
| **RTF（Real-Time Factor）** | 处理耗时 / 音频时长 | 推理 RTF < 0.5（留余量），系统 RTF < 1 |
| **打断响应延迟** | 用户开口 -> 系统停止播报 | < 500ms |
| **吞吐（tokens/s）** | 语音 token 生成速率 / 播放需求速率 | 生成速率 > 12.5~25 token/s（实时音频需求） |
| **轮转自然度** | 话轮间隔分布 vs 人类 200~250ms | 分布峰值接近人类均值 |

注意区分：**RTF 衡量「算得动」，TFRT 衡量「回得快」**。全双工系统还要求持续生成速率大于播放消耗速率（12.5Hz x 码本数），否则会「卡顿欠载」。

## 8. PyTorch 示例：双流 time-synchronous 前向骨架

```python
import torch
import torch.nn as nn

class DuplexSpeechLLM(nn.Module):
    """
    Moshi 式双流全双工骨架:
    - 输入: 用户流 (client) 的语义 token + 声学码 (已由 Mimi codec 提取)
    - 输出: 模型流 (model) 的语义 token (inner monologue) + 声学码
    - 帧率: 12.5 Hz (每步 80ms)
    """
    def __init__(self, d_model=2048, n_layers=24, semantic_vocab=32000,
                 acoustic_codebooks=11, codebook_size=2048):
        super().__init__()
        # 嵌入: 用户语义/声学 + 模型语义/声学 (声学码逐码本嵌入后求和)
        self.client_sem_emb = nn.Embedding(semantic_vocab, d_model)
        self.model_sem_emb = nn.Embedding(semantic_vocab, d_model)
        self.acoustic_embs = nn.ModuleList(
            [nn.Embedding(codebook_size, d_model)
             for _ in range(acoustic_codebooks)])
        self.backbone = nn.TransformerEncoder(
            nn.TransformerEncoderLayer(d_model, nhead=16,
                                       dim_feedforward=4 * d_model,
                                       batch_first=True),
            num_layers=n_layers)
        # 输出头: inner monologue 文本轨 + 各声学码本轨
        self.model_sem_head = nn.Linear(d_model, semantic_vocab)
        self.acoustic_heads = nn.ModuleList(
            [nn.Linear(d_model, codebook_size)
             for _ in range(acoustic_codebooks)])

    def step(self, client_sem, client_acoustic, model_sem_prev, model_acoustic_prev):
        """
        单个时间步 (80ms):
        client_sem:        [B]        用户语义 token
        client_acoustic:   [B, K]     用户 K 个码本的声学码
        model_sem_prev:    [B]        模型上一步语义 token
        model_acoustic_prev:[B, K]    模型上一步声学码
        返回: 模型本步 语义 token logits + 声学码 logits
        """
        x = self.client_sem_emb(client_sem) + self.model_sem_emb(model_sem_prev)
        for k, emb in enumerate(self.acoustic_embs):
            x = x + emb(client_acoustic[:, k]) + emb(model_acoustic_prev[:, k])
        # 实际实现中所有历史步进 backbone (此处示意单步)
        h = self.backbone(x.unsqueeze(1))[:, 0]
        return self.model_sem_head(h), [head(h) for head in self.acoustic_heads]

if __name__ == "__main__":
    m = DuplexSpeechLLM()
    B, K = 2, 11
    sem_logits, ac_logits = m.step(
        client_sem=torch.randint(0, 32000, (B,)),
        client_acoustic=torch.randint(0, 2048, (B, K)),
        model_sem_prev=torch.randint(0, 32000, (B,)),
        model_acoustic_prev=torch.randint(0, 2048, (B, K)),
    )
    print(sem_logits.shape, len(ac_logits), ac_logits[0].shape)
    # 延迟估算: 每步必须 < 80ms (12.5Hz), 否则跟不上实时音频流
```

## 9. 总结与最佳实践

* **全双工 = 同时听说 + 打断 + 自然轮转 + backchannel**，其架构基石是 time-synchronous 双流建模（Moshi），关键训练技巧是 Inner Monologue（文本轨锚定语义）。
* **打断实现分层**：级联系统靠 AEC+VAD 前端强杀（注意 AEC 残留导致误打断）；原生模型靠语义内生停止，更自然但更难训。
* **延迟预算要背量级**：级联 ~1~2s（VAD 500ms+ 是大头），端到端 300~800ms（GPT-4o 均值 320ms），人类自然话轮间隔 200~250ms 是终极标尺。
* **指标**：TFRT/首响延迟 < 500ms、RTF < 1、打断响应 < 500ms、持续生成速率 > 帧率 x 码本数。
* **delay 减半三板斧**：消灭 VAD 等待（语义 endpointing / 预测式 turn-taking）、全链路流式化（chunk 到即算即合成）、低帧率 codec（12.5Hz Mimi）+ 会话级 KV cache。
