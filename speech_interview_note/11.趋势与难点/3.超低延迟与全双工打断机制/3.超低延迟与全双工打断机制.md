# 3. 超低延迟与全双工打断机制

## 1. 概述

人类对话的轮转间隔（turn-taking gap）中位数约 **200~250ms**（Stivers et al., 2009, 跨语言研究）。用户对语音助手的体感「聪明程度」很大程度上取决于**响应延迟**：超过 1 秒用户开始怀疑「卡了吗」，超过 2 秒对话节奏崩塌。而真实对话的核心特征是**全双工（full-duplex）**：边听边说、随时打断（barge-in）、及时闭嘴。

本文拆解两个主题：

1. **延迟预算**：级联式与端到端系统各环节的毫秒级账本；
2. **全双工机制**：打断检测、回声消除（AEC）、端点检测、预测抢答（anticipation）与时间同步架构（Moshi 双流）。

```
半双工 (对讲机式):  用户 ──说──> [ 系统: 听完->想->说 ] ──> 用户    (轮流, 无打断)
全双工 (自然对话):  用户 ══听/说══> [ 系统: 并行听+说, 可被打断, 可抢答 ] <══听/说══ 系统
```

## 2. 延迟预算分解（Latency Budget）

### 2.1 级联系统（ASR -> LLM -> TTS）

定义：**用户停止说话的时刻 $t_0$** 到**系统第一个可听音频帧出现**的时间差，为响应延迟。

| 环节 | 典型耗时 | 组成与说明 |
| --- | --- | --- |
| **端点检测** | 300~800 ms | 等待静音确认（VAD hangover / tail silence）。是级联系统**最大的单项** |
| **ASR 尾句定稿** | 50~200 ms | 流式 ASR 的 partial->final 修正；chunk 尾部对齐 |
| **LLM 首 token** | 100~500 ms | TTFT：prefill 长度、网络 RTT、推理引擎调度（vLLM 下 P50 约 100~200ms） |
| **LLM 首句攒词** | 100~300 ms | TTS 按句/分词粒度喂入需等 LLM 攒够首个合成单元 |
| **TTS 首音频包** | 50~200 ms | 声学模型首帧 + vocoder + 流式 chunk 打包 |
| **网络/客户端** | 50~150 ms | WebSocket/WebRTC RTT、播放缓冲（jitter buffer 常预留 40~80ms） |
| **合计** | **650ms ~ 2.2s** | 级联系统实际分布常见 P50≈1s、P95≈2s |

### 2.2 端到端（原生 S2S / 流式一体化）

| 环节 | 典型耗时 | 说明 |
| --- | --- | --- |
| 端点/接话决策 | 0~160 ms | 模型在时间对齐流上逐步决策，无需长静音确认 |
| 模型首步生成 | 80~200 ms | 12.5Hz codec 一步出 80ms 音频；prefill 语音上下文 |
| codec 解码 | 10~40 ms | 流式 decoder/vocoder |
| 网络传输 | 30~100 ms | 流式传输 token 或音频帧 |
| **合计** | **200~500 ms** | Moshi 实测理论延迟约 200ms 量级；GPT-4o Realtime 官方均值约 300~500ms（含网络） |

**结论（面试常考）**：级联系统的延迟大头是「端点检测等待 + 管道串联排队」，原生 S2S 的提速不只来自模型统一，更来自**把端点决策从规则等待变成模型的逐步行为决策**。

## 3. 打断（Barge-in）检测方案

用户在系统说话过程中开口，系统应当**迅速停止播放、开始听**。打断响应时间（从用户开口到系统静音）要求 **< 200ms**，否则用户感知「它没在听」。

### 3.1 检测信号分级

```
用户麦克风输入 ──> [AEC 回声消除] ──> 残留信号
                                        │
        ┌───────────────┬───────────────┼────────────────┐
        ▼               ▼               ▼                ▼
   能量检测          VAD 检测        流式 ASR partial   语义判断
   (快/易误触)      (Silero/webrtc)  (词级证据)        (LLM: 是真打断?)
        └────── 融合决策 (score = w1*E + w2*V + w3*S + w4*M) ──────┘
```

| 方案 | 原理 | 延迟 | 误触/漏检风险 |
| --- | --- | --- | --- |
| **能量阈值** | AEC 后残留能量 > 阈值持续 >N ms | 20~50ms | 噪声环境误触率高；只适合作辅助信号 |
| **VAD（Silero/webrtc）** | 神经网络语音/非语音判决，Silero 单帧 ~1ms CPU | 30~80ms | 对电视声、旁人说话无法区分目标用户 |
| **流式 ASR 证据** | partial 结果出现实词（>1~2 个字）才判打断 | 150~400ms | 延迟大，但显著降误触 |
| **语义打断** | LLM 对 partial 文本判断「是否构成打断意图」（如提问、否定「停/不是」） | +100ms | 最准，只能做最后一级仲裁 |
| **融合决策** | 加权/级联：能量+VAD 快速触发，ASR+语义在 300ms 内确认或撤销 | 分层 | 工业主流 |

### 3.2 打断后的动作链

1. **立即静音播放**（TTS 播放端 fade-out 10~20ms 防爆音）；
2. **作废已生成未播内容**：级联系统要取消 LLM 生成队列；S2S 系统要把模型行为切到「听」状态并截断 KV cache 中假设性的自说内容；
3. **上下文记账**：被打断的半句话以「已播部分 + 未播部分」何种形式进入对话历史，直接影响后续连贯性（工业实现常保留完整生成文本于上下文，但标注为 interrupted）。

## 4. 回声消除（AEC）与半双工问题

### 4.1 为什么 AEC 是全双工的前提

系统外放的声音会被自己麦克风重新拾取（声学回声）。若不消除：

* VAD 会把「系统自己的声音」误判为用户说话，触发**自我打断**（系统把自己打断，无限循环静音）；
* ASR 会把系统语音转写进用户话语，污染上下文。

这就是很多廉价音箱只能**半双工**（播放期间不拾音，播放即「聋」）的根因：没有可靠 AEC，只能二选一。

### 4.2 AEC 原理

自适应滤波器（频域 NLMS / 自适应远端模型）估计回声路径传递函数 $\hat{h}$，从麦克风信号中减去远端参考的滤波估计：

$$e(t) = y(t) - \hat{h} * x_{ref}(t)$$

其中 $y$ 为麦克风信号，$x_{ref}$ 为系统播放的远端参考（已知）。残留部分再经 **NLP（非线性抑制）/残余回声抑制（RES）** 与降噪。

### 4.3 工程方案与流水线

```
[播放参考 x_ref] ──┐
                   ├─> [AEC: webrtc AEC3 / speex] ─> [RES + NS(谱减/RNN)] ─> [VAD/ASR]
[麦克风 y] ────────┘
        (手机/音箱本地执行; 服务端只收处理后的单流)
```

* **传统**：WebRTC AEC3 / speex / PulseAudio echo-cancel。免提、强混响、非线性失真（喇叭削顶）场景下残余回声仍会漏过。
* **深度学习 AEC**：Microsoft Interspeech 2020 AEC Challenge 推动的一类方案（输入 = 麦克风信号 + 远端参考的堆叠频谱，输出掩蔽/复数比例因子），对非线性回声抑制显著更强，可级联在传统 AEC 之后作深度残余抑制（DRES）。
* **服务端兜底**：即使端侧有 AEC，服务端还可跑一路 VAD 与「回声重叠检测」（用户语音 token 与系统播放内容高相似即判回声）。

## 5. 端点检测与预测抢答（Anticipation）

### 5.1 端点检测（Endpointing / Voice Activity End Detection）

级联系统用静音时长判停：`tail-silence = 500~800ms` 常用。改进方向：

* **动态阈值**：根据当前句子的句法完整性（LM 打分）、语速调整等待时长。句子完整则短等待（300ms），句子未完则长等待（1s+）；
* **基于部分结果的语言学端点**：Google 的「Smart Endpointer」用 LLM 判断 partial 转写是否为完整语义单元；
* **权衡指标**：端点提前会**截断**（cut-off，用户还没说完就被接话，极伤体验），端点延后增加延迟。可用「在固定截断率（如 1%）下的平均延迟」做横向对比。

### 5.2 预测抢答（Anticipation / Future Prediction）

人类能在对方说完前就**预判结束并开始准备发声**。模型化手段：

* **VAP（Voice Activity Projection）类转向预测模型**：输入双方语音的 SSL 特征，预测未来若干窗口（如 0.2/0.4/.../2.0s）内双方各自的说话概率，输出「此刻接话/继续等」的决策。用大量双人流水日志训练。
* **Moshi 的训练目标天然含预测**：时间对齐双流下，模型在用户流每帧只看到 $u_{\le t}$ 就要输出 $s_t$，学会在用户句尾前一帧就降低自己输出概率、在合适时刻立刻起音--等价于隐式学到了 turn-taking 与 anticipation。
* **抢答的风险**：预测错误即**插话截断用户**，必须配合「起音后若检测到用户仍在说则立即退让」的让话（yield）策略。评估指标见第 7 节。

## 6. 全双工时间同步架构

### 6.1 Moshi 双流（Duplex Streaming）回顾

```
                 时间对齐 (12.5 Hz, 每步 80ms)
   t=1        t=2        t=3        t=4
U: u1         u2         u3         u4          <- 用户流 (Inst, 语义token)
M: [s1,x1]   [s2,x2]   [s3,x3]   [s4,x4]       <- 模型流 (Out: 音频token s + 内心文本 x)

每步注意力: M_t 可看 U_{<=t}, M_{<t};  U 流无梯度回传(不生成)
模型行为:   s = <pad> 表示本步"闭嘴", s = <audio> 表示本步"发声"
```

要点：

* **并行听与说**：模型流每步都在产出（可以是静音 pad token），用户流每步都在输入，因此「说话时仍在听」在架构层面成立；
* **行为标签从数据中来**：训练语料里「双方同时说话的帧」「模型让话的帧」提供了监督信号，模型学到让话、抢话、应答「嗯哼」backchannel 等对话行为；
* **延迟公式**：算法延迟 $\approx$ 帧长（80ms）+ 模型一步前向（<100ms GPU）+ 网络，总 200~300ms。

### 6.2 级联系统的「伪全双工」改造

| 组件 | 改造 |
| --- | --- |
| 播放侧 | 全程开麦 + AEC，播放时 VAD 持续跑（打断检测不关闭） |
| LLM | 生成可中断：用户打断时丢弃未播 KV 前缀，注入打断事件 token 继续生成 |
| TTS | 流式合成 + 播放队列可清空（flush） |
| 状态机 | speaking / listening / overlapped 三态，overlap 态进入打断确认逻辑 |

## 7. 实时对话评估指标

| 指标 | 定义 | 参考量级 |
| --- | --- | --- |
| **响应延迟分布** | $t_{\text{first audio}} - t_{\text{user end}}$，报 P50/P95 | 级联 P50≈1s；S2S P50≈300~500ms；人类≈250ms |
| **打断响应时间** | 用户开口到系统静音 | 目标 <200ms |
| **截断率（cut-off rate）** | 用户未说完即被接话的比例 | <1~2% |
| **误打断率（false barge-in）** | 噪声/回声触发系统停止的比例 | <0.5%/轮 |
| **让话成功率（yield）** | 抢答后被用户继续说、系统正确退让的比例 | 越高越好 |
| **轮转 F1（turn-taking F1）** | 对「谁在何时该说」的帧级/轮级预测的 F1 | 对话式评测核心指标 |
| **backchannel 自然度** | 「嗯/对」类反馈词的出现时机合理性 | 人工评 |

## 8. PyTorch 示例：融合打断检测与端点状态机

```python
import time
from dataclasses import dataclass, field

@dataclass
class DuplexState:
    """级联/端到端通用的全双工对话状态机"""
    playing: bool = False          # 系统正在播放
    user_speaking: bool = False
    silence_ms: float = 0.0        # 连续静音累计
    vad_frames: int = 0            # 连续语音帧数
    events: list = field(default_factory=list)

class BargeInDetector:
    """
    分层融合打断检测:
      L1: AEC 残留能量 (20ms 窗)  -> 快速候选
      L2: Silero VAD 语音概率     -> 确认有人声
      L3: 流式 ASR partial 实词数 -> 抑制电视声/咳嗽
      L4: 语义仲裁(可选, LLM)     -> "停/不是/等一下"
    """
    def __init__(self, e_thr=-35.0, vad_thr=0.6, min_word=1, hangover_ms=120):
        self.e_thr, self.vad_thr = e_thr, vad_thr
        self.min_word, self.hangover_ms = min_word, hangover_ms
        self.speech_start = None

    def on_frame(self, rms_db: float, vad_p: float, partial_text: str,
                 playing: bool, now: float) -> str:
        # 回放中才需要打断检测; 播放中要求更高置信度(防自回声)
        vad_p_eff = vad_p if not playing else vad_p * 1.15
        energy_hit = rms_db > self.e_thr
        voice_hit = vad_p_eff > self.vad_thr
        words = [w for w in partial_text.strip().split() if len(w) >= 1]

        if playing:
            if energy_hit and voice_hit and len(words) >= self.min_word:
                return "BARGE_IN"          # 触发: 停止播放, 丢弃未播文本, 切换listening
            return "KEEP_PLAYING"

        # 非播放态: 端点检测逻辑
        if energy_hit and voice_hit:
            if self.speech_start is None:
                self.speech_start = now
            return "USER_SPEAKING"
        else:
            if self.speech_start is not None:
                silence = (now - self.speech_start) * 1000
                # 动态静音阈值: partial 文本若为完整问句则短等待
                thr = 500 if partial_text.strip().endswith(("?", "吗", "呢")) else 800
                if silence >= thr:
                    self.speech_start = None
                    return "ENDPOINT_HIT"  # 触发: 送入LLM/S2S开始生成
            return "SILENCE"


class ResponseLatencyTracker:
    """响应延迟与打断响应时间打点"""
    def __init__(self):
        self.t_user_end = None
        self.t_barge_open = None

    def mark_user_end(self):        self.t_user_end = time.time()
    def mark_bargein_open(self):    self.t_barge_open = time.time()
    def mark_first_audio(self):
        assert self.t_user_end
        return (time.time() - self.t_user_end) * 1000   # ms, 目标 P50<500
    def mark_system_mute(self):
        assert self.t_barge_open
        return (time.time() - self.t_barge_open) * 1000  # ms, 目标 <200


if __name__ == "__main__":
    det, st = BargeInDetector(), DuplexState()
    # 模拟: 系统播放中, 第5帧出现用户语音+ASR实词 -> 触发打断
    for i, (rms, vp, txt) in enumerate([
            (-50.0, 0.05, ""), (-48.0, 0.1, ""), (-30.0, 0.8, "停"),
            (-29.0, 0.9, "停下"), (-49.0, 0.1, "")]):
        action = det.on_frame(rms, vp, txt, playing=True, now=i * 0.02)
        print(f"frame{i}: rms={rms}dB vad={vp} text='{txt}' -> {action}")
```

## 9. 总结与最佳实践

* **延迟优化优先级**（级联系统）：端点检测（省 300~500ms）> LLM TTFT（推理引擎/首句策略）> TTS 首包 > 网络；端到端系统的核心是低帧率 codec + 逐步行为决策。
* **打断检测用分层融合**：能量+VAD 快触发、ASR+语义慢确认，打断响应 <200ms 且误打断 <0.5%。
* **AEC 是全双工的地基**：端侧 AEC3/深度 AEC + 服务端回声相似度兜底；没有 AEC 就只能半双工。
* **全双工架构首选时间对齐双流**（Moshi 范式）：把「何时说/何时听」变成模型的逐帧行为决策，配 VAP 类转向预测做 anticipation；务必配套让话与截断率监控。
* **指标体系**：响应延迟分布（P50/P95）、打断响应时间、截断率、误打断率、轮转 F1，上线必须全量打点。
