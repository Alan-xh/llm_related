# 3. 低延迟与C++推理部署

## 1. 概述

语音模型的**实时部署**（流式 ASR/TTS、端侧语音助手）对延迟极其敏感：单 chunk 前向必须在几十毫秒内完成，全链路（采集->特征->推理->解码->下发）通常要求 < 200ms。Python 生态（PyTorch/TF）的 GIL、解释器开销与部署体积使其难以满足要求，因此工业界实时链路几乎全部采用 **C++ 推理栈**：

* 模型导出为 ONNX/TensorRT engine，脱离 Python 运行时；
* C++ 实现音频采集、特征提取、推理调用、解码与后处理全流程；
* 目标是**确定性延迟**：P99 与 P50 接近，无 GC/调度导致的尖刺。

典型量级目标：流式 Zipformer encoder 单 chunk（640ms 输入）在桌面 CPU 上前向 < 30ms；端到端 partial 延迟 P99 < 250ms。

---

## 2. 推理栈对比：ONNX Runtime / TensorRT / libtorch

| 维度 | ONNX Runtime (ORT) | TensorRT (TRT) | libtorch (TorchScript) |
| --- | --- | --- | --- |
| **支持平台** | CPU(GPU(NPU(XPU，全平台 | 仅 NVIDIA GPU | CPU/CUDA，随 PyTorch |
| **模型格式** | ONNX | ONNX 转 engine（按 GPU 架构编译） | TorchScript (.pt) |
| **性能** | CPU 上最优之一；GPU 上不如 TRT | NVIDIA GPU 上极致（算子融合+kernel 自动调优） | GPU 接近原版 PyTorch，CPU 一般 |
| **优化手段** | ORT graph transform、INT8 量化、Execution Provider（CUDA/TensorRT/CoreML/NNAPI/QNN） | FP16/INT8/FP8、layer fusion、dynamic shape profile、kernel tuning | 与训练代码零转换成本 |
| **动态 shape** | 原生支持好 | 需预设 optimization profile 范围 | 原生支持 |
| **部署体积** | ~20MB runtime | ~1GB+ 依赖 CUDA | ~500MB+ |
| **典型场景** | 端侧/服务器通用、sherpa-onnx 生态 | 云端 GPU 高吞吐/低延迟批服务 | 快速原型、与训练强耦合的复杂控制流 |

选型经验：

* **端侧（手机/IoT）**：ONNX Runtime（可挂 CoreML/NNAPI EP）或 NCNN/MNN；
* **云端 GPU 流式**：TensorRT engine（FP16 为主）或 ORT + TensorRT EP；
* **验证/离线**：libtorch 快速对齐训练侧结果。

## 3. C++ 部署流水线

### 3.1 整体架构

```
┌────────────────────────── C++ 进程 ──────────────────────────┐
│                                                              │
│  [Audio Thread]  采集/收包 -> Ring Buffer (lock-free)        │
│       │  读写指针无锁交换, 不做任何重活                        │
│       ▼                                                      │
│  [Feature Thread] 环形缓冲取 PCM -> FBank(逐帧增量) -> 特征队列│
│       ▼                                                      │
│  [Worker Thread(s)] 攒 chunk -> ONNX/TRT 前向 -> 解码        │
│       │                (Transducer greedy/beam, CTC collapse)│
│       ▼                                                      │
│  [Post Thread] 标点/ITN/热词 -> 回调/网络下发 partial/final   │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 音频采集与 Ring Buffer

音频线程的最高原则是**不做任何可能阻塞的事**（no allocation、no lock、no log），否则丢帧/爆音。生产者-消费者之间用**无锁环形缓冲**：

```cpp
// 单生产者-单消费者无锁 ring buffer（音频场景够用）
class RingBuffer {
public:
    explicit RingBuffer(size_t capacity_samples)
        : buf_(capacity_samples), capacity_(capacity_samples) {}

    // 仅 audio thread 调用；写满则丢弃最旧数据（overrun 计数）
    void write(const int16_t* src, size_t n) {
        size_t tail = tail_.load(std::memory_order_relaxed);
        for (size_t i = 0; i < n; ++i) {
            buf_[(tail + i) % capacity_] = src[i];
        }
        tail_.store(tail + n, std::memory_order_release);
    }

    // 仅 consumer 调用
    size_t read(size_t max_n, std::vector<int16_t>& out) {
        size_t head = head_.load(std::memory_order_relaxed);
        size_t tail = tail_.load(std::memory_order_acquire);
        size_t avail = tail - head;                 // 允许回绕: 用单调计数
        size_t n = std::min(avail, max_n);
        out.resize(n);
        for (size_t i = 0; i < n; ++i)
            out[i] = buf_[(head + i) % capacity_];
        head_.store(head + n, std::memory_order_release);
        return n;
    }
private:
    std::vector<int16_t> buf_;
    size_t capacity_;
    std::atomic<size_t> head_{0}, tail_{0};         // 单调递增采样计数
};
```

要点：索引用**单调递增计数**（避免回绕歧义）、容量按最大抖动设计（如 2 倍 chunk）、overrun/underrun 计数暴露为监控指标。

### 3.3 增量特征提取

流式场景下 FBank 必须逐帧增量计算，而非每次对整段重算：

* 维护**帧移状态**：每凑满 `frame_shift`（如 160 sample @10ms）产出一帧；帧长窗（如 400 sample）允许跨 chunk 取数；
* FFT 复用预分配 buffer；mel 滤波矩阵做**离线转置 + 定点化**；
* CMVN（倒谱均值归一化）：流式下用**递推均值**或用训练语料全局均值，避免未来信息泄漏。

```cpp
class StreamingFbank {
public:
    // 每 chunk 调用: 返回本 chunk 新产生的帧数
    int AcceptPCM(const int16_t* pcm, size_t n);
    // 输出 [new_frames, 80] 的 float 特征, 拼进 encoder 缓存
    const float* GetNewFrames(int* num_frames);
private:
    std::vector<float> pcm_pending_;   // 跨 chunk 残余采样
    int frames_emitted_ = 0;
    // mel 滤波、log、dither、preemphasize、cmvn 状态 ...
};
```

### 3.4 模型推理与内存池 / 零拷贝

* **预分配 IO buffer**：session 创建后用 `io_binding`（ORT）把输入输出绑定到**固定显存/内存地址**，避免每次前向 malloc/free 与 H2D 拷贝；
* **内存池**：beam search 的 hypothesis、token 扩展 buffer 全部池化复用，稳定后零分配（allocation-free steady state），这是消除 P99 尖刺的关键；
* **零拷贝**：特征线程写入的 buffer 直接作为 inference 输入（对齐与 stride 预先设计好，避免 memcpy）；输出 logits 用 ring/views 分发给解码器，不整块复制；
* **线程绑定**：audio thread 绑核隔离（`pthread_setaffinity_np`），避免被 worker 的计算线程抢占导致丢帧。

```cpp
// ORT IO Binding + 预分配输入 (伪代码)
ort::Env env;
ort::Session session(env, u"encoder.onnx",
                     ort::SessionOptions{});   // SetIntraOpNumThreads(2)
// 固定 shape: [1, chunk_frames + cached, 80]
std::vector<float> feats(cap_ * 80, 0.f);
ort::Value in = ort::Value::CreateTensor<float>(
    mem_info, feats.data(), feats.size(),
    dims.data(), dims.size());                 // 零拷贝: 直接包 feats
// 预分配输出同理, run 循环中反复复用
```

## 4. 线程模型

### 4.1 生产者-消费者拓扑

```
[Audio] --lock-free ring--> [Feature] --queue--> [Worker x N] --> [Post/Net]
  实时优先级                   普通               普通(CPU密集)        普通
```

* **audio thread vs worker 的隔离**是第一原则：audio 线程只搬数据（微秒级），任何推理/解码都不许出现在它上面；
* **worker 数量** = 模型前向线程数（ORT intra-op）与并发会话数的乘积权衡；单路流式通常 1 个 worker + intra-op 2~4 线程；
* 队列用有界 blocking queue（满时丢旧/合并），背压显式化而非无限堆积。

### 4.2 GPU 场景的批处理线程

多路会话共享一张 GPU 时，由 **batcher 线程**在固定节拍（如每 320ms）收集所有就绪会话的 chunk，拼 batch 一次前向，再拆开发回各会话 decoder（continuous batching）。这把 GPU 利用率从 ~15%（batch=1）提升到 60%+，同时保持单路延迟不变。

## 5. RNN-T / CTC 的 C++ 解码实现要点

### 5.1 流式 RNN-T 贪婪解码

C++ 实现的核心是**跨 chunk 的状态保持**：encoder 的 cache（attention/conv 状态）、predictor 的 hidden/cell、已发射 token 序列。伪代码：

```cpp
struct TransducerState {
    std::vector<float> predictor_hidden_, predictor_cell_;  // LSTM 状态
    std::vector<int>   emitted_tokens_;                     // 历史 token
    int max_symbols_per_frame_ = 4;   // 死循环保护
};

// 每收到一个 encoder 输出帧 h_t 调用一次
void DecodeFrame(const float* enc_out,      // [enc_dim]
                 TransducerState& st,
                 Ort::Session& joint_sess,
                 std::vector<int>& new_tokens) {
    for (int emitted = 0; emitted < st.max_symbols_per_frame_; ) {
        // 1. predictor 前向(单步, 复用 hidden 状态)
        auto pred = PredictorStep(st.emitted_tokens_.back(), st);
        // 2. joint: 拼接 [enc; pred] -> Linear+tanh -> logits [vocab+1]
        auto logits = JointForward(enc_out, pred);
        int argmax = Argmax(logits);
        if (argmax == BLANK) return;            // 帧结束, 等下一帧
        st.emitted_tokens_.push_back(argmax);   // 同一帧继续发射
        new_tokens.push_back(argmax);
        ++emitted;
    }
}
```

工程要点：

1. **`max_symbols_per_frame`**（通常 3~5）防止同一帧无限发射 token；
2. predictor 单步前向单独建一个 ONNX（`predictor.step.onnx`），避免每 token 重跑整个序列；
3. joint 网络很小（两层 Linear），可选直接 C++ 手写 GEMM；
4. 输出 token 立即过 detokenizer（BPE merge）下发 partial。

### 5.2 CTC 流式解码

CTC 流式比 RNN-T 简单：每帧一个分布，无内循环。要点：

* **greedy + 塌陷**：逐帧 argmax，按 `blank` 与重复折叠；但流式下**末尾 token 需暂存**——若当前帧与暂存 token 相同且中间无 blank，不能输出（可能是拉长音）；
* **prefix beam search（C++）**：维护 beam of `(prefix, p_blank, p_nonblank)`，每帧扩展；实时场景 beam 取 4~8，配合外部 LM shallow fusion：
  $\text{score} = \log P_{ctc} + \lambda \log P_{lm}$；
* **延迟发射**：最后一个未确认 token 至少等下一帧（确认中间出现 blank 或不同 token）再下发，避免 partial 抖动。

## 6. 性能剖析（Profiling）

### 6.1 分阶段打点

上线前必须建立**每会话全链路 trace**，按阶段打点（单调时钟）：

| 阶段 | 典型预算(640ms chunk, 桌面 CPU) | 优化手段 |
| --- | --- | --- |
| 采集 + ring buffer | < 1ms | 绑核、无锁 |
| Fbank 特征 | 2~5ms | 增量计算、定点化、NEON/AVX |
| encoder 前向 | 15~30ms | ONNX 图优化、INT8、剪帧缓存 |
| predictor+joint 解码 | 3~10ms | 单步模型、GEMM 手写、token 剪枝 |
| 后处理 + 下发 | 1~5ms | 零拷贝序列化 |
| **合计** | **~25~50ms/chunk** | RTF ≈ 0.04~0.08 |

### 6.2 工具与长尾分析

* **工具**：`perf`（CPU 热点）、`nsys/Nsight`（GPU timeline）、ORT 自带 `verbose profiling`（每个算子耗时 JSON）、`eBPF` 抓调度延迟；
* **P99 尖刺常见来源**：(1) 内存分配/页错误 -> 池化 + `mlockall`；(2) CPU 频率调度 -> performance governor / 绑核；(3) GC 式抖动不存在于 C++，但 `malloc` 争锁会有 -> tcmalloc/jemalloc 或全池化；(4) GPU 上多路批冲突 -> batcher 节拍与超时强制 flush；
* **度量口径**：报告 P50/P95/P99 与 max，而非平均值；长尾通常由 1% 的慢 chunk 决定用户体验。

## 7. 高频面试问答 (Q&A)

### Q1: 为什么实时 ASR 不直接用 Python 部署？C++ 带来了什么？

**答**：Python 的 GIL 使音频线程与推理线程无法真并行，解释器与动态分配带来毫秒级不确定尖刺，且打包部署重。C++ 提供：无锁数据结构、确定性的内存管理（池化后稳态零分配）、线程绑核与实时优先级、小体积嵌入端侧。经验数字：同一 encoder，Python 服务 P99 常见 100ms+ 尖刺，C++ 化后 P99/P50 < 1.5。

### Q2: audio thread 与 worker thread 为什么要严格隔离？怎么实现？

**答**：音频回调通常每 10~20ms 触发一次，任何阻塞（锁、malloc、系统调用、日志）都会导致丢帧爆音且不可恢复。实现：audio thread 只做一件事——把采样写入无锁 ring buffer；用 `pthread_setaffinity_np` 绑独立核 + `SCHED_FIFO` 提升优先级；与消费者之间用 SPSC ring（单生产者单消费者，head/tail 原子变量 + acquire/release 语义）。

### Q3: ONNX Runtime 部署流式模型时有哪些必做的优化？

**答**：(1) 导出时固定 chunk shape 与 cache 长度，减少动态 shape 重排；(2) `SetIntraOpNumThreads` 控制线程数并与绑核配合；(3) IO Binding 预分配输入输出，消除每步 malloc 与 H2D 拷贝；(4) 图优化等级开满（`ORT_ENABLE_ALL`）；(5) 开启 profiling 定位最慢算子，必要时 INT8 量化 encoder；(6) 把 predictor 拆成 step 模型避免重复前向。

### Q4: RNN-T 的 C++ 解码器为什么要拆成多个 ONNX 模型？

**答**：流式解码存在三种不同节奏的计算：encoder 按 chunk、predictor 按 token（且要单步递归）、joint 每帧每 token 调用。若合成一个大图，每次发射 token 都要重跑无变化的 encoder 输出。拆成 `encoder.onnx`（chunk 级，带 cache IO）、`predictor.step.onnx`（单步，hidden 状态在 IO 上往返）、joint（极小，可手写）后，各部分独立复用，解码延迟下降明显，这是 sherpa-onnx 等框架的标准做法。

### Q5: 如何把流式 ASR 的 P99 延迟从 300ms 压到 150ms？

**答**：先用 profiling 定位预算分布，再逐项压：(1) chunk 从 640ms 减到 320ms（直接砍缓冲延迟）；(2) encoder INT8 + 算子融合降前向；(3) 池化 + `mlockall` 消除分配尖刺；(4) 绑核与 CPU governor 固定为 performance；(5) GPU 多路时 batcher 设 flush 超时避免某路等待拼 batch；(6) partial 下发走贪心，beam/二遍纠错异步化，不阻塞 partial 路径。

## 8. 总结与最佳实践

* **推理栈选型**：端侧与通用 CPU 选 ONNX Runtime（可挂 CoreML/NNAPI EP），NVIDIA GPU 低延迟选 TensorRT，快速验证用 libtorch。
* **流水线三原则**：audio thread 极简（无锁 ring buffer）、worker 计算与音频隔离（绑核）、稳态零分配（IO binding + 内存池）。
* **解码器工程化**：RNN-T 拆 encoder/predictor.step/joint 三图，`max_symbols_per_frame` 防死循环；CTC 注意末尾 token 的延迟确认与 blank 折叠规则。
* **性能可观测**：分阶段打点 + P50/P95/P99 报告；长尾尖刺的四大来源（分配、调度、频率、批冲突）逐一排除，延迟优化永远从 profiling 出发。
