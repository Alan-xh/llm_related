# 1. 流式ASR与TTS

## 1. 概述

在实时语音交互系统（语音助手、实时字幕、同声传译、语音对话机器人）中，**流式（Streaming）处理**是核心链路：音频一边采集、一边传输、一边识别/合成，结果一边增量返回。

* **流式 ASR（Streaming ASR）**：不等整句说完才出字，而是在每收到一个 chunk（通常 100~640ms）后就输出 **partial（中间）结果**，并在语音段结束时给出 **final（稳定）结果**。工业界指标通常要求端到端延迟 < 300~500ms。
* **流式 TTS（Streaming TTS）**：不等整段文本与整段音频全部生成，而是以句子/子句为单位增量合成，边合成边播放，核心指标是 **首包延迟（Time to First Audio, TTFA）**，通常要求 < 200~300ms。

ASR 与 TTS 串联（如语音对话、同传）时，两者的延迟预算会叠加，因此必须做**全链路延迟预算管理（Latency Budget）**。

## 2. 流式 ASR 服务架构

### 2.1 整体架构

一个典型的云端流式 ASR 服务由四层组成：**接入层（网关）-> 会话层（Session 管理）-> 识别引擎（Encoder + Decoder）-> 后处理层（ITN、标点、顺滑）**。

```
 客户端 (App / Web / IoT)
    │  ① 音频流 (PCM 16kHz 16bit, chunk=100~320ms)
    ▼
┌────────────────────────────────────────────────────┐
│  接入层: WebSocket / gRPC 双向流网关                │
│  (鉴权、限流、协议封装、断线重连、session sticky)    │
└───────────────────────┬────────────────────────────┘
                        ▼
┌────────────────────────────────────────────────────┐
│  会话层: Session Manager                            │
│  - chunk 缓冲与组帧 (拼成 640ms 模型输入)            │
│  - VAD 状态机 (speech/silence 翻转)                 │
│  - partial/final 下发策略                           │
└───────────────────────┬────────────────────────────┘
                        ▼
┌────────────────────────────────────────────────────┐
│  识别引擎: Streaming Encoder (Zipformer/Conformer)  │
│           + Transducer/CTC Decoder + Rescoring LM  │
└───────────────────────┬────────────────────────────┘
                        ▼
┌────────────────────────────────────────────────────┐
│  后处理: ITN (数字规整)、标点、顺滑 (口语顺滑)、      │
│          热词替换、敏感词过滤                        │
└────────────────────────────────────────────────────┘
```

### 2.2 WebSocket 与 gRPC 双向流对比

流式 ASR 的通信协议必须是**双向流（full-duplex）**：上行推音频、下行推识别结果。

| 维度 | WebSocket | gRPC (bidirectional streaming) |
| --- | --- | --- |
| **协议层** | 基于 HTTP/1.1 Upgrade（或 HTTP/2） | 基于 HTTP/2 |
| **数据编码** | 文本帧 + 二进制帧（音频用二进制） | Protobuf（强类型，序列化开销极小） |
| **接口契约** | 需自行定义消息格式（常用 JSON 信封 + binary frame） | `.proto` 文件强约束，自动生成多语言 SDK |
| **流控/超时** | 需自行实现心跳 (ping/pong) 与背压 | 内置 flow control、deadline、cancel 语义 |
| **浏览器支持** | 原生支持（Web 场景首选） | 浏览器需 gRPC-Web + 代理转译 |
| **典型选择** | Web/App 端、开源项目 (funasr_server) | 服务间调用、大厂内部微服务 |

消息协议设计要点（面试常问）：

* **上行**：二进制音频帧（裸 PCM/Opus）+ 少量带外信令（`start`/`continue`/`end`、采样率、编码格式）。
* **下行**：JSON/Protobuf 消息，包含 `result`（文本）、`is_final`（bool）、`begin_time/end_time`（字级时间戳）、`confidence`。
* **心跳与超时**：客户端静默超 60s 自动断开；服务端每 chunk 都应回包（哪怕空结果），作为「链路活着」的隐式心跳。

### 2.3 Chunk 发送策略

客户端按固定时长切片发送音频，服务端按模型要求组帧：

```
客户端发送 (chunk=160ms, 2560 samples @16kHz):
 |--c1--|--c2--|--c3--|--c4--|--c5--|--c6--|--c7--| ...
          ▲ 100ms 网络抖动容忍

服务端组帧 (模型输入 stride=320ms, lookahead=160ms):
 |------c1+c2------|------c3+c4------|------c5+c6------|
          encoder 第1次前向        第2次前向          第3次前向
          (可输出 partial #1)      (partial #2)       (partial #3)
```

* **chunk 大小权衡**：chunk 越小延迟越低，但 encoder 前向次数越多、GPU 利用率越差（batch 难以凑大）；chunk 越大 RTF 越好但延迟上升。工业界常见 320~640ms。
* **对齐问题**：网络抖动会导致 chunk 到达不均匀，服务端必须以**采样点计数**为准做缓冲（如凑满 N 个 sample 才前向），而不是以「收到几次消息」为准。
* **backpressure（背压）**：客户端发送速度天然等于实时（1x），一般不会压垮服务端；真正要防的是**重连风暴**与**并发会话数**。

### 2.4 Partial vs Final 结果

| 维度 | Partial（中间结果） | Final（最终结果） |
| --- | --- | --- |
| **触发时机** | 每个 encoder chunk 前向后立即下发 | VAD 检测到句尾静音 / 用户主动 end-of-stream |
| **稳定性** | 可变（后缀会被改写：`你好` -> `你好世界`） | 不可变（该语音段的最终定稿） |
| **解码策略** | 贪心 / 小 beam（速度优先） | 大 beam + LM Rescoring / 二遍模型纠错（质量优先） |
| **用途** | 实时字幕、UI 实时上屏 | 下游任务（翻译、对话、存储） |

关键实现细节：

1. **Partial 的「回退改写」**：chunk-based encoder 带 lookahead 时，最后一个 lookahead 窗内的输出不稳定，下发 partial 时通常**截掉末尾 1~2 个字**（或标记为 tentative），避免用户看到反复跳变的字。
2. **二遍纠错（Two-pass）**：一句结束后，把整句音频送入更强的非流式模型（如 Paraformer/Whisper/Conformer-Rescoring）重打分，final 结果用二遍替换一遍。典型架构：**Zipformer-Transducer（一遍流式）+ Conformer AED（二遍纠错）**。
3. **Endpoint 检测**：final 的触发依赖 VAD 尾点静音（如静音 600~800ms 判句尾），或模型自带的 endpoint head。

```python
# 流式 ASR 服务端伪代码 (WebSocket)
async def asr_session(ws):
    session = StreamingSession(sample_rate=16000, chunk_samples=5120)
    async for msg in ws:
        if isinstance(msg, bytes):
            session.push_pcm(msg)                    # 缓冲音频
            for feat_chunk in session.pop_frames():  # 凑满模型帧
                partial = session.infer_partial(feat_chunk)
                await ws.send(json.dumps(
                    {"text": partial, "is_final": False}))
            if session.vad.speech_ended():           # 尾点静音触发
                final = session.infer_final_rescore()
                await ws.send(json.dumps(
                    {"text": final, "is_final": True}))
                session.reset_utterance()
```

## 3. 流式 TTS

### 3.1 非流式 vs 流式 TTS

传统 TTS（如 FastSpeech2 + HiFi-GAN）是**句子级**的：整句文本 -> 整段 mel -> 整段波形。用户要等数秒才能听到第一个字，无法满足实时对话。流式 TTS 的核心思想是**把文本切小、把合成流水线化、把播放提前**。

```
非流式 TTS:
Text(整句) ──> Frontend ──> Acoustic Model(整句) ──> Vocoder(整段) ──> 播放
                      总延迟 = T_text + T_acoustic(全句) + T_vocoder(全段) ≈ 2~5s

流式 TTS (sentence-level 流水线):
LLM 输出 token 流:
 [今天] [天气] [很好] [，] [我们] [去] [公园] [吧]
    │       │       │
    ▼       ▼       ▼
  切句1   切句2   切句3          ──> 文本队列
           │ (流水线并行)
           ▼
  Acoustic: 逐 chunk 生成 mel   ──> mel 队列
           │
           ▼
  Vocoder: 逐 chunk 生成 wav    ──> 播放队列 ──> 扬声器
首包延迟 ≈ 首个短句出现时间 + 首包 mel 合成 + 首包波形 ≈ 150~300ms
```

### 3.2 Sentence-level 流水线与切句策略

* **切句粒度**：按标点（，。？！；）切分；LLM 对话场景下在 LLM 流式输出中检测到「可合成单元」（一个子句/短语，6~15 字）即触发合成。
* **粒度权衡**：切太碎 -> 韵律差（ prosody 断裂，语调不自然）；切太大 -> 首包延迟上升。折中方案：**首句切小（抢首包），后续句切大（保韵律）**。
* **跨句上下文**：合成第 k 句时可把前文文本作为条件送入 acoustic model，缓解韵律断裂。
* **播放端缓冲**：播放器维护 jitter buffer（如 200ms 音频），当合成速度跟不上播放速度（欠载）时需要 TTS 引擎加速（time-stretch）或等待。

### 3.3 首包优化（TTFA 优化）

TTFA = 首个合成单元产出时间 + 首包合成时间 + 网络传输 + 播放器启动。常用手段：

1. **首句切短**：LLM 流式输出中首个 4~8 字即触发合成。
2. **模型侧**：acoustic model 只合成首个 mel chunk（如 20~40 帧）即送 vocoder，不等整句。
3. **vocoder chunk 化**：流式 vocoder（见 3.4）首 chunk 波形生成 < 30ms。
4. **预热**：会话建立时提前 warm up（CUDA context、kernel JIT、首个空前向）。
5. **流式协议**：音频用 Opus 编码传输（16kHz 24kbps 即接近透明），下行按 chunk 播放。

### 3.4 增量式 / 流式 Vocoder

传统 HiFi-GAN 生成时感受野覆盖整段，且有上采样卷积的 future 依赖。流式化方案：

* **因果化 + 有限 lookahead**：把 vocoder 的所有卷积改为 causal（或只允许 lookahead 数十 ms），逐 chunk（如 640ms）生成波形，chunk 间维护卷积的 padding cache。
* **Streaming HiFi-GAN / LPCNet**：LPCNet 用 LSTM 天然因果，适合流式；神经声码器 RTF 可做到 0.02~0.05（GPU）。
* **预生成 cache**：对每个 speaker 预热固定 prompt mel，减少首 chunk 的状态冷启动。

### 3.5 大模型 TTS 的流式化：VALL-E / CosyVoice

**VALL-E（Neural Codec Language Model）**：把 TTS 建模为 codec token 的语言模型（AR 生成第一层 codec + NAR 生成其余层）。

* 流式难点：AR 解码器逐 token 生成，1 秒音频约 75 个 token（Encodec 24Hz 下 ~75 token/s），RTF 依赖 LLM 推理速度；NAR 层需要多遍迭代。
* **VALL-E 流式化思路**：`VALL-E 的 chunk 流式`——AR 模型每生成一个 codec chunk（如 1s）就交给 vocoder 播放，AR 与播放流水线并行；配合 **CLLM（Consistency LLM）** 把多步 AR 并行化为常数步，可将 RTF 从 0.9 降到 0.1 量级。

**CosyVoice（阿里）**：`Flow-matching based` 的非自回归 acoustic model + `HiFi-GAN` vocoder，支持流式：

* 文本前端 + LLM（Qwen 系）生成 semantic token（流式逐 token 输出）；
* **CosyVoice 的流式方案**：semantic token 攒够一个 chunk（如 25 token，约 1s 音频）即触发 flow-matching block 流式生成 mel，mel 再流式过 vocoder。官方 `cosyvoice-cli` 的 `stream=True` 模式 TTFA 可压到 150ms 级。
* 对比：flow-matching block 内是并行去噪（几十步 ODE），单 chunk 内延迟可控；LLM 部分（semantic token AR）是延迟大头，靠 chunk 切小 + KV cache + 投机解码优化。

```
CosyVoice 流式流水线:

 Text ──> LLM(AR, KV cache) ──sem token──┐ (攒 25 token ≈ 1s)
                                         ▼
                              Flow-Matching (chunk去噪)
                                         │ mel chunk
                                         ▼
                              HiFi-GAN (causal, chunk)
                                         │ wav chunk (~1s)
                                         ▼
                                    播放队列
```

### 3.6 ASR + TTS 端到端延迟预算表

以「语音对话：用户说话 -> ASR -> LLM -> TTS -> 用户听到」为例（数字为工业界典型量级）：

| 阶段 | 组件 | 典型延迟 | 优化手段 |
| --- | --- | --- | --- |
| 1 | 采集 + chunk 缓冲 | 40~160ms | 减小 chunk、边采边发 |
| 2 | 网络上行 (RTT 1/2) | 20~50ms | 就近接入、QUIC |
| 3 | VAD 尾点判定 | 500~800ms（静音确认） | 调小 endpoint 静音阈值 / 模型 endpoint |
| 4 | 流式 ASR final 出字 | 50~150ms | chunk 内贪心、二遍异步 |
| 5 | LLM 首 token | 200~500ms | KV cache、投机解码、小模型首答 |
| 6 | TTS 首包合成 (TTFA) | 150~300ms | 首句切短、流式 vocoder |
| 7 | 网络下行 + 播放启动 | 30~80ms | Opus、jitter buffer 预设 |
| - | **合计（不含说话结束等待）** | **约 1.0~2.0s** | 用户感知阈值：<1.5s 优秀 |

> 注：第 3 项「尾点静音确认」往往是大头。打断（barge-in）场景下，可让 LLM/TTS 在 ASR partial 阶段就**投机预取**（speculative prefetch），句尾确认后立即播放，把感知延迟压到 1s 以内。

## 4. 关键工程问题

### 4.1 会话亲和与状态管理

流式 encoder/decoder 携带跨 chunk 状态（attention cache、predictor state）。重连时必须恢复到同一后端实例（session sticky），或把状态外置（session serialization），否则识别结果会跳变。

### 4.2 GPU batching 与延迟矛盾

流式会话是「细水长流」，单路前向 batch=1，GPU 利用率低。工业界方案：

* **continuous batching**：多个并发会话的 chunk 在同一 step 攒 batch 前向（要求各会话同构模型、同 chunk 调度）；
* 单卡可承并发数百路（如 Zipformer-sm 流式在 T4 上 200+ 并发，RTF < 0.05/路）。

### 4.3 打断（Barge-in）与回声消除

全双工对话中，TTS 播放的音频会被麦克风录回来。必须 AEC（回声消除）后再进 ASR/VAD；检测到用户打断（VAD 触发 + 能量门槛）后，TTS 立即停止播放、ASR 状态重置。

## 5. 高频面试问答 (Q&A)

### Q1: 流式 ASR 中 partial 和 final 分别怎么实现？为什么 partial 会「变来变去」？

**答**：partial 在每个 chunk 前向后用贪心/小 beam 立即解码下发；final 在 VAD 判定句尾后，可选用大 beam + LM rescoring 或二遍非流式模型纠错后下发。partial 跳变的原因：(1) chunk-based encoder 的 lookahead 窗内输出依赖未来帧，新帧到来后后缀被改写；(2) 二遍纠错模型会整句替换。工程上对 partial 的末尾 1~2 个字做 tentative 标记或延迟下发，可显著减少 UI 跳变。

### Q2: WebSocket 和 gRPC 在流式 ASR 中怎么选？

**答**：浏览器/Web 端选 WebSocket（原生支持、穿透防火墙容易）；服务间调用与多端统一 SDK 选 gRPC 双向流（Protobuf 强类型、HTTP/2 多路复用、内置流控/超时/取消）。大厂常见做法：对外暴露 WebSocket 网关，内部微服务间走 gRPC。

### Q3: 流式 TTS 的首包延迟（TTFA）怎么优化到 200ms 以内？

**答**：(1) 切句策略上首句取 4~8 字的最小可合成单元；(2) acoustic model 流式输出首个 mel chunk（非整句）；(3) vocoder 因果化，首 chunk 波形 < 30ms；(4) 会话预热（CUDA context/kernel JIT）；(5) 与 LLM 串联时用 streaming 接口逐 token 检测切句点，避免等 LLM 整句生成完。

### Q4: VALL-E / CosyVoice 这类大模型 TTS 做流式的难点是什么？

**答**：难点在 AR 语义/codec token 生成是逐 token 的，一秒音频对应几十个 token，LLM 解码速度直接决定 RTF；NAR 层（或 flow-matching）虽能并行但需要攒够 chunk。解法：chunk 流水线（token 生成与 vocoder 播放并行）、CLLM/投机解码加速 AR、KV cache 复用、flow-matching 的 block 内少步去噪。

### Q5: ASR+LLM+TTS 全链路 2 秒延迟，怎么定位哪个环节是瓶颈？

**答**：全链路埋点（trace_id 贯穿），分段记录：chunk 到达时间戳、每次前向耗时、VAD endpoint 触发时刻、LLM 首 token 时间、TTS 首包时刻、播放器起播时刻。经验上三个大头：VAD 尾点静音确认（500~800ms，可用可打断策略或减阈值）、LLM 首 token（投机解码/首答小模型）、TTS TTFA（首句切短 + 流式 vocoder）。优化优先级应从用户感知路径（首字节响应）出发。

## 6. 总结与最佳实践

* **流式 ASR**：WebSocket/gRPC 双向流 + chunk 缓冲组帧 + partial/final 双档结果 + 二遍纠错；chunk 大小在延迟与吞吐之间权衡（320~640ms 常见）。
* **流式 TTS**：sentence-level 流水线（LLM token 流 -> 切句 -> acoustic chunk -> 因果 vocoder chunk -> 播放），首包优化是第一目标（TTFA < 200~300ms）。
* **大模型 TTS 流式**：VALL-E 靠 chunk 流水线 + CLLM 加速 AR；CosyVoice 靠 semantic token 攒 chunk + flow-matching 块内并行 + 流式 HiFi-GAN。
* **全链路预算**：画延迟预算表，逐项压测埋点；VAD 尾点、LLM 首 token、TTS 首包是三大优化杠杆；全双工场景必须做 AEC 与 barge-in。
