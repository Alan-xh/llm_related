# 部署优化面试题（推理部署与低延迟优化高频考点）

## 1. 概述

语音算法工程师的面试中，「模型训得准」只占一半分数，另一半在「**部署跑得好**」：如何把 ASR/TTS/VAD 模型以低延迟、高吞吐、低资源的方式部署到云端 GPU 集群与端侧设备，并在真实流量下保持稳定（P99 长尾可控、不 OOM、可热更新）。

本文档按照面试官的典型考察路径组织：**部署目标对比（云端吞吐 vs 端侧延迟）-> 核心机制（量化公式、并发模型）-> 工业界实战（长尾延迟 P99、OOM、热更新）-> 高频问答**。涉及量化细节、C++ 流水线、VAD 等专题可配合本目录前四篇文档阅读。

---

## 2. 部署目标对比：云端吞吐 vs 端侧延迟

云端与端侧是两套完全相反的优化目标，面试中先讲清「为谁优化」最能体现工程判断力。

```
云端部署 (Server)                          端侧部署 (On-Device)
┌───────────────────────┐                  ┌───────────────────────┐
│  客户端 x 10000+      │                  │  单用户, 单进程        │
│    │ WebSocket/gRPC   │                  │    │ 本地麦克风        │
│    ▼                  │                  │    ▼                  │
│  LB -> GPU 推理集群    │                  │  CPU/NPU 本地推理      │
│  目标: 吞吐(路/GPU)、  │                  │  目标: RTF、内存、耗电 │
│        成本(元/小时)   │                  │        峰值内存、冷启动│
└───────────────────────┘                  └───────────────────────┘
```

| 维度 | 云端流式 ASR/TTS 服务 | 端侧语音助手 |
| --- | --- | --- |
| **第一指标** | 吞吐（并发路数/GPU）、单路成本 | RTF（<0.3 单核）、P99 延迟 |
| **延迟要求** | 端到端 < 300~500ms，P99 接近 P50 | chunk 内前向 < 50~100ms |
| **资源模型** | GPU 显存（决定 batch 上限） | peak RSS（如 < 100MB）、耗电 mAh/min |
| **批处理** | continuous batching，多路拼 batch 提高 GPU 利用率 | **batch=1**，固定 shape，反批处理优化 |
| **精度选择** | FP16 / BF16 为主，INT8 为省显存 | INT8/INT4 weight-only 为主流 |
| **稳定性挑战** | 长尾 P99、OOM（显存碎片）、热更新 | 冷启动、机型长尾（低端机）、温控降频 |
| **典型数字** | T4/A10 单卡流式 Zipformer 200+ 路，RTF<0.05/路 | sherpa-onnx INT8 模型 30~50MB，中端机 RTF 0.1~0.3 |

核心结论：**云端优化「每 GPU 并发路数」（分子是路数、分母是卡时成本），端侧优化「每焦耳的延迟」**。同一个模型在两侧的最优部署形态（精度、shape、线程模型）完全不同。

## 3. 核心机制一：量化与精度-性能权衡

### 3.1 量化公式（必背）

非对称量化（激活值常用）：

$$x_q = \text{clamp}\left(\text{round}\left(\frac{x}{s}\right) + z\right), \quad s = \frac{x_{\max} - x_{\min}}{2^b - 1}, \quad z = \text{round}\left(-\frac{x_{\min}}{s}\right), \quad \hat{x} = s(x_q - z)$$

对称量化（权重常用，per-channel）：

$$s = \frac{\max |w|}{2^{b-1} - 1}, \quad z = 0, \quad \hat{w} = s \cdot w_q$$

QAT 的直通估计器（STE）：前向插入 fake-quantize 误差，反向梯度直通 $\partial \hat{x}/\partial x \approx 1$。

### 3.2 精度阶梯与决策树

| 档位 | 配置 | 速度(FP32=1x) | 精度损失 | 适用 |
| --- | --- | --- | --- | --- |
| FP16/BF16 | 全半精度 | ~2x | ~0 | 云端 GPU 默认 |
| W8A8 INT8 | 全整型 | 2~4x | 0.1~0.5% CER | 语音 encoder、端侧 |
| weight-only INT8/4 | 权重 INT8/4 + 激活 FP16 | 1.2~2x（带宽 bound 时更高） | 近 0 | LLM/TTS（激活离群值） |
| KV cache INT8 | 解码缓存量化 | 内存减半 | <0.5% | 长序列自回归 |

决策路径：先 PTQ（percentile/KL 校准）-> 掉点换混合精度（敏感层跳过）-> 再不满足上 QAT。详细展开见《4. 端侧量化与低延迟优化》。

## 4. 核心机制二：并发模型（Concurrency Model）

### 4.1 云端：continuous batching + 异步流水线

流式会话天然 batch=1（每路每 320ms 一个 chunk），GPU 利用率仅 ~15%。解法：

```
             ┌──────────── Batcher (固定节拍 320ms) ────────────┐
 路A chunk ─►│  攒所有就绪会话 -> 拼 batch [B, T, 80] 一次前向    │──► 拆分回各路
 路B chunk ─►│  (设 flush 超时, 某路就绪必须 <40ms 内被带上)      │    decoder
 路C chunk ─►└──────────────────────────────────────────────────┘
```

* **batcher 节拍与超时**：节拍决定单路额外缓冲延迟（节拍的一半均值），超时 flush 保证长尾；
* **两级流水**：encoder（GPU、批处理）与 decoder/predictor（CPU、per-session 状态）异步解耦，互不阻塞；
* **并发容量估算**：单卡并发路数 ≈ GPU 前向吞吐 / 每路 chunk 频率。例：A10 上 640ms chunk、batch=32 前向耗时 60ms -> 每秒可处理 32/0.06≈533 chunk -> 每路 1.56 chunk/s -> 理论 ~340 路，打七折（波动/重连）约 240 路。

### 4.2 端侧：三级流水 + 绑核

```
[Audio 线程] --无锁ring--> [特征线程] --queue--> [Worker] --> 下发/回调
 绑小核, 实时优先级                                绑大核, batch=1
```

* audio 线程只搬数据（无锁、无分配），worker 做特征/前向/解码；
* 稳态零分配（IO 预分配 + 内存池）是消除 P99 尖刺的关键（详见《3. 低延迟与C++推理部署》）。

### 4.3 线程/协程模型对比

| 模型 | 适用 | 风险 |
| --- | --- | --- |
| 每路一个线程 | 路数少（<100） | 上下文切换、栈内存 |
| 线程池 + 任务队列 | 通用 CPU 解码 | 队列堆积需背压 |
| 协程（asio/fiber） | 万级长连接接入层 | 与 CPU 密集推理需分离调度 |
| GPU 单流 + batcher | encoder 前向 | 节拍延迟 vs 利用率权衡 |

## 5. 工业界实战问题

### 5.1 长尾延迟（P99）治理

P99 尖刺的四大来源与对策：

| 来源 | 现象 | 对策 |
| --- | --- | --- |
| **内存分配/页错误** | 偶发 +10~50ms | 池化、`mlockall`、预分配 IO、tcmalloc |
| **CPU/GPU 调度** | 周期性尖刺 | 绑核、performance governor、GPU MPS/MIG 隔离 |
| **批处理冲突** | 多路拼 batch 时个别路被拖慢 | flush 超时、batch 上限、按延迟 SLO 分池 |
| **下游依赖** | 后处理/LM rescore 卡顿 | 异步化、降级开关（尖刺时关二遍纠错） |

实践：全链路 trace 打点（chunk 到达/前向开始结束/下发），按 P50/P95/P99/max 报警；先消灭「系统性长尾」（批冲突、GC 式抖动），再磨「调度噪声」。

### 5.2 OOM 与显存管理

* **显存碎片**：长时间运行后大 batch 分配失败 -> 用显存池（预分配最大 shape）、PyTorch 侧 `expandable_segments` 或 ORT arena 配置；
* **并发上限控制**：并发路数 x per-session 状态（attention cache、decoder state）必须小于显存预算；入口限流排队而非硬扛；
* **KV cache 增长**（TTS/LLM 解码）：设最大序列长度上限 + 超长强制 finalize；KV cache INT8 量化减半；
* **优雅降级**：OOM 时降 batch、关二遍、踢空闲会话，而不是进程崩溃。

### 5.3 热更新（模型不停机发布）

```
新模型就绪 -> 灰度: 新会话走新版本, 存量会话不动 (session sticky)
        -> 按实例/按流量百分比放量 -> 全量 -> 旧实例回收
```

* **双 buffer 加载**：新模型权重加载到独立内存（mmap 新文件），原子切换指针，加载期间旧模型继续服务；
* **会话粘性**：流式会话有状态，切版本必须「存量走旧、增量走新」；网关按 session id 哈希路由；
* **快速回滚**：旧版本权重常驻或可秒级 mmap 回来；模型效果监控（线上无标注 -> 用 proxy 指标：平均句长、delete/insert 比、用户重说率）异常自动回切。

## 6. 高频面试问答 (Q&A)

### Q1: 云端流式 ASR 服务的容量怎么估算？一台卡能跑多少路？

**答**：三步：(1) 压测单卡前向吞吐（chunk/s）——固定 batch 前向耗时，得 chunk 处理率；(2) 每路 chunk 频率 = 1/chunk 时长（如 320ms 即 3.1 chunk/s）；(3) 并发路数 = 吞吐/频率，再按 CPU 解码线程、显存状态、网络抖动打 6~7 折。同时验证单路 P99 延迟在 SLO 内——路数翻倍但 P99 爆掉没有意义。必须报告「路数 + P99 + RTF」三元组。

### Q2: 为什么流式服务普遍用 continuous batching 而不是请求级 batching？

**答**：流式请求生命周期长（分钟级），传统 static batching 要等凑满或超时，延迟不可控且会话何时结束不可知。continuous batching 按 chunk 粒度在固定节拍内收集就绪会话拼 batch，会话可随时加入/退出，兼得吞吐（GPU 利用率 15%->60%+）与延迟（节拍一半的均值缓冲）。

### Q3: 线上 P99 延迟是 P50 的 10 倍，怎么排查？

**答**：先看打点分段定位阶段（采集/网络/前向/解码/下发）。常见四类：内存分配与页错误（池化 + mlockall）、调度（绑核、频率 governor、是否有别的进程抢核）、批处理冲突（batcher 节拍内个别路等待拼 batch -> 设 flush 超时）、下游同步依赖（二遍纠 score、标点服务同步调用 -> 异步化或降级）。修复后必须用 P99/P50 比值（目标 < 2~3）做回归监控，而不是只看均值。

### Q4: 服务运行几天后 OOM，怎么定位与治理？

**答**：先区分「真泄漏」还是「碎片/增长」。(1) 真泄漏：heap profiler（tcmalloc/jemalloc profiling、valgrind）抓泄漏栈，常见是每会话新建执行器/ Ort::Value 未释放；(2) 状态增长：长会话的 cache/beam 无上限 -> 设 session 最大时长与 beam 上限；(3) 显存碎片：预分配最大 shape 的池 + arena。治理上：入口按显存预算限流、OOM 时降级（降 batch/关二遍）而非崩溃、canary 实例跑 72h 内存斜率监控进发布门槛。

### Q5: 如何不停机把新 ASR 模型发到线上？

**答**：热更新三要素：双 buffer 原子切换（新权重 mmap 加载、指针原子换，老权重引用计数归零后释放）、会话粘性（存量会话继续用旧模型直到自然结束，新会话走新模型）、灰度回滚（按实例/百分比放量，线上 proxy 指标异常自动回切）。注意新旧模型的 tokenizer/特征维度若不兼容，必须升版本号隔离路由，不能原地替换。

### Q6: 端侧和云端部署同一个模型，优化手段有什么不同？

**答**：云端目标是吞吐/成本：FP16 + continuous batching + 显存池 + 二遍纠错模型（算力富余换精度）；shape 可动态、batch 可变。端侧目标是单路延迟/耗电/内存：INT8/weight-only 量化 + 固定 shape（batch=1）+ 算子融合 + delegate 到 NPU + 三级流水绑核 + 模型蒸馏缩小（DistilWhisper 范式）；机型长尾要求在最低支持机型上 RTF 达标才算过关。

### Q7: 量化掉点了，你的排查与修复顺序是什么？

**答**：(1) 确认对比基线公平（同一测试集、同一解码配置）；(2) 逐层量化敏感性分析，定位掉点层（常见：encoder 末层、joint、LayerNorm 密集段）；(3) 校准侧：换 percentile/KL、扩校准数据覆盖真实分布；(4) 混合精度：敏感层跳过量化；(5) 仍不行上 QAT（fake-quant + STE 短 finetune）；(6) 极端场景换 weight-only。修复后把量化 CER 损失门槛（如 <0.3%）写进 CI。

### Q8: RTF 是什么？流式场景下 RTF 和延迟是一回事吗？

**答**：RTF = 处理耗时 / 音频时长，衡量「跟不跟得上」（RTF < 1 才可能实时）；延迟 = 一个字/结果从被说出到被用户看到的时间，由 chunk 缓冲、算法 lookahead、前向、网络、下发共同决定。RTF=0.3 的系统延迟仍可能是 500ms（chunk 大、串行流水线）；RTF 只要求 <1，延迟才是用户体验指标。面试要点：能拆出延迟公式 延迟 ≈ chunk/2 + lookahead + 前向 + 排队 + 网络，并逐项给优化手段。

## 7. 总结

* **先定目标再优化**：云端优化吞吐与每路成本（continuous batching、显存预算），端侧优化 RTF、P99 与耗电（量化、batch=1、流水线绑核）；两端的精度选择、shape 策略、线程模型完全不同。
* **量化是第一杠杆**：牢记非对称/对称公式与 per-channel 权重默认配方；PTQ -> 混合精度 -> QAT 的阶梯修复路径；LLM/TTS 场景 weight-only + KV cache INT8。
* **稳定性三板斧**：长尾治理（池化、绑核、flush 超时、异步降级）、OOM 治理（显存池、状态上限、优雅降级）、热更新（双 buffer、会话粘性、灰度回滚）。
* **度量文化**：路数/RTF/P99 三元组、P99:P50 比值、peak RSS、耗电全部进 CI 与报警；所有优化从 profiling 出发，用数据闭环验证。
