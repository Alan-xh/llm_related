# 5. 流式ASR与Chunk-based解码

## 1. 概述

**流式 ASR（Streaming / Online ASR）** 是指在用户说话的同时，系统边接收音频边出字，partial 结果随语音推进不断刷新，说话结束后很快给出 final 结果的识别范式；与之相对的**非流式 ASR（Offline ASR）** 则等待整句/整段音频收集完毕后一次性解码，可以利用完整的双向上下文换取最低的 WER。

端到端模型的普及让"流式"变得困难：Whisper 类 AED 的全局 Cross-Attention、Conformer 的双向 Self-Attention 本质上都要"看到未来"，而流式恰恰要求**未来不可见**。**Chunk-based（分块）方案**因此成为工业界的主流答案：把长音频切成固定时长的 chunk，每个 chunk 只允许"偷看"有限的 lookahead（右侧上下文），历史上下文通过 cache/state 传递。

```
   Offline (非流式)                       Streaming (流式, Chunk-based)
 ┌────────────┐  ┌────────┐            ┌──────────────────────────────┐
 │ 完整音频    │─>│ Encoder│ (双向)      │ PCM 流 ──> VAD/切分 ──> chunk │
 │ (整句 5~30s)│  └───┬────┘            │   c1    c2    c3    c4  ...  │
 └────────────┘      ▼                 │   ▼     ▼     ▼     ▼        │
                 ┌────────┐            │  out1  out2  out3  out4      │
                 │ Decoder│──> 一次性   │  "你"  "你好" "你好世" ...    │
                 └────────┘    输出     └──────────────────────────────┘
   延迟: 数秒                延迟: 首包 200~400ms, 词级平均 200~800ms
```

典型延迟预算：语音助手类端到端（含网络与后处理）要求 **100~600ms**；实时字幕可放宽到 1~5s；同声传译 2~5s。准确率代价：流式相对 offline 通常有 **10%~50% 的相对 WER 劣化**，具体取决于 chunk/lookahead 大小与状态传递设计。

## 2. 流式 vs 非流式：延迟指标体系

### 2.1 两种范式对比

| 维度 | Offline（非流式） | Streaming（流式） |
| --- | --- | --- |
| **编码器上下文** | 全句双向（BiLSTM / 全局 Attention） | 有限上下文（chunk + lookahead + 跨块状态） |
| **准确率（WER）** | 最优（基线） | 相对劣化 10%~50% |
| **延迟** | 秒级（整句等待 + 一次性推理） | 100ms~1s 级 |
| **解码驱动方式** | 全局 Beam / 自回归生成 | 帧同步（CTC/RNN-T）或受限自回归（AED） |
| **典型模型** | Whisper、SenseVoice、Paraformer | Zipformer-Transducer、Chunk Conformer、Emformer |
| **典型场景** | 字幕后期、音频转写、数据挖掘 | 语音助手、实时字幕、同传、输入法、直播审核 |

### 2.2 关键延迟指标

| 指标 | 定义 | 体验合格线（量级） |
| --- | --- | --- |
| **首包延迟（First Token Latency）** | 从用户开始说话（VAD 触发）到屏幕出现第一个字 | < 400ms |
| **词级平均延迟（Average Token Latency）** | 每个 token 的真实发声时刻与上屏时刻之差的均值（需对齐脚本测量） | 200~800ms |
| **尾部延迟（Finalization Latency）** | 最后一个字说完到 final 文本确定 | 500~1000ms |
| **算法延迟（Algorithmic Latency）** | 由 chunk/lookahead 决定的模型固有等待，与硬件无关 | 100~1000ms |
| **工程延迟（Engineering Latency）** | 网络、缓冲、特征提取、推理、解码、渲染等系统开销 | 50~300ms |

### 2.3 算法延迟 vs 工程延迟

端到端延迟可分解为：

$$T_{\text{e2e}} = \underbrace{(N_{\text{chunk}} + N_{\text{right}})\cdot \Delta t}_{T_{\text{algo}}\ （算法延迟）} + \underbrace{T_{\text{net}} + T_{\text{buf}} + T_{\text{feat}} + T_{\text{infer}} + T_{\text{decode}}}_{T_{\text{eng}}\ （工程延迟）}$$

* **算法延迟**：设编码帧移 $\Delta t$（10ms 帧经 4x 下采样后为 40ms），chunk 长度为 $N_{\text{chunk}}$ 帧、右上下文 $N_{\text{right}}$ 帧。chunk 内**首帧**的输出要等"整个 chunk + lookahead"收齐，故上界 $T_{\text{algo}} = (N_{\text{chunk}} + N_{\text{right}})\Delta t$，chunk 末帧仅等 $N_{\text{right}}\Delta t$，平均约 $(N_{\text{chunk}}/2 + N_{\text{right}})\Delta t$。
* **工程延迟**：WebSocket/gRPC 传输（30~100ms）、采集缓冲（20~40ms）、Fbank 特征（<5ms）、GPU 推理（chunk 前向 10~50ms）、CTC/RNN-T 增量解码（<10ms）、渲染。工程优化靠**流水线并行、GPU chunk 合并、cache-aware 推理**（见第 7 节）。

> **面试要点**：被问"你们的延迟是多少"时，必须先澄清是算法延迟还是端到端工程延迟、是首包还是词级平均——这四个数字完全不同。

## 3. Chunk-based 流式架构

### 3.1 Chunk 划分与 Left/Right Context

```
                        ◄──────────── 本步计算时可见范围 ────────────►
 ┌────────────────────────┬────────────────────┬────────────────────┐
 │     Left Context       │      Chunk i       │   Right Context    │
 │  历史 chunk (可选保留)  │  本步输出的帧        │   lookahead (未来)  │
 │  经 K/V cache 复用      │  典型 320ms ~ 1s    │   典型 160~640ms    │
 └────────────────────────┴────────────────────┴────────────────────┘
 ▲                        ▲                  ▲                    ▲
 0                     chunk 起点          chunk 结束        lookahead 结束
                          T_algo(上界) = chunk 时长 + lookahead 时长
```

* **Left Context（左上下文）**：理论上可无限（通过 K/V cache 保留全部历史），实践中为控制计算量常截断到最近 1~10 个 chunk。
* **Right Context（lookahead）**：少量未来帧能显著降低插入错误与同音字错误。经验上 **lookahead 对准确率的边际收益远大于同等的 chunk 增量**，因此工业配置里 lookahead 通常小于 chunk（如 chunk 640ms + lookahead 160~320ms）。
* **下采样卷积**：4x 下采样的 Conv2d（7 帧入 1 帧出）自带约 3 帧（30ms）额外 lookahead，且跨 chunk 需要保留尾部帧（tail padding）保证连续性。

### 3.2 Chunk-based Conformer（WeNet U2 系列）

对标准 Conformer 的流式改造：

1. **Attention 限制**：Self-Attention 的每个 query 只能看见"历史（经 cache）+ 当前 chunk + lookahead"内的 key，训练时用 banded mask 模拟（支持随机 chunk 长度的 **dynamic chunk 训练**，一个模型同时覆盖流式与非流式）；
2. **卷积因果化**：深度卷积（Depthwise Conv）模块改为 causal 版本或仅带 1 帧右 padding；
3. **相对位置编码**天然兼容受限注意力，无需改动。

```
              key 帧 ─────────────►
 query  ┌──────────────────────────┐
 帧 ↓   │ ■ ■ ■ ■ □ □ □ □ □ □ □ □  │   ■ = 可见 (历史 + 当前 chunk + lookahead)
        │ ■ ■ ■ ■ ■ ■ ■ □ □ □ □ □  │   □ = mask 为 -inf 的未来帧
        │ ■ ■ ■ ■ ■ ■ ■ ■ ■ □ □ □  │   (对角线右上三角 + 超出 lookahead 的部分)
        │ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ □  │
        └──────────────────────────┘
```

典型配置：chunk_size=16（下采样帧，16 × 40ms = 640ms），配 RNN-T 头即 WeNet 经典流式方案；U2 的 **2-pass 融合**（流式出 partial，endpoint 后用 offline 分支重打分出 final）兼顾延迟与准确率。

### 3.3 Emformer（Efficient Memory Transformer）

Meta 提出的低延迟流式 Transformer 编码器，核心是**块处理（Block Processing）+ 记忆（Memory）**：

* 把序列切成不重叠的 block，block 内做全注意力；
* 每个**历史 block 压缩成少量摘要向量（summary embedding）**存入 memory，当前 block 的 query 对 memory 做注意力——以极小的计算量保留长程历史（解决"左上下文截断"问题）；
* 未来信息通过一个小的 2D 卷积 lookahead 引入（量级几十毫秒），算法延迟主要由 block/chunk 尺寸决定；
* 训练用 **截断 BPTT**，模拟推理时的分段前向。

### 3.4 Zipformer

k2-fsa 提出的多分辨率编码器，流式版本是当前开源流式 ASR 的最优基线之一：

* **Zip 结构**：把不同下采样率（如 8x/4x/2x）的 encoder block **串联交错堆叠**，低帧率层建模长时依赖、高帧率层保留细节；
* **流式改造**：全部卷积因果化 + **跨 chunk 状态传递（state carrying）**——每个模块把自己的中间状态（卷积尾帧、注意力所需上下文）带入下一个 chunk，推理时逐 chunk 携带状态前进；
* **双 lookahead**：短程 lookahead（数百毫秒量级）+ 长程 lookahead（可达 1s 以上）级联，用少量额外延迟换取接近 offline 的上下文；
* 配合 **Pruned RNN-T**（stateless predictor）组成完整的流式 Transducer 系统。

### 3.5 流式编码器对比

| 模型 | 流式机制 | 左上下文 | lookahead | 算法延迟量级 | 特点 |
| --- | --- | --- | --- | --- | --- |
| **Chunk Conformer (U2)** | banded attention mask + cache | 有限/无限（cache） | chunk 右侧若干帧 | 320ms~1s | 实现简单，一个模型流式/非流式统一 |
| **Emformer** | block processing + summary memory | memory 摘要（有损） | 小卷积 lookahead | 数百 ms（block 决定） | 显存/计算高效，适合端侧 |
| **Zipformer** | 因果卷积 + 跨块状态传递 + 双 lookahead | 状态携带（无损） | 短程+长程两级 | 320ms~1.3s | 精度最高，工程复杂度高 |
| **LC-BLSTM（老式）** | 有限上下文 BLSTM | 全历史（前向层） | 每层 R 帧 | 200~400ms | 用于早期 Google 流式 RNN-T |

## 4. CTC / RNN-T / AED 三种架构的流式化方案对比

### 4.1 CTC 的流式化

* 只需把 encoder 改成 chunk-based，解码天然帧同步：每个新编码帧做 argmax，非 blank 且与前一帧不同即输出。
* 局限：**帧间条件独立、无语言模型能力**，流式小上下文下同音字/口音错误更突出，工业上常外挂 WFST/LM 做浅融合（shallow fusion）或用 n-gram 重打分。
* 注意 **token 实际延迟 > 算法延迟**：CTC 概率峰值通常滞后真实发声边界 100~300ms（blank 占比高、声学边界模糊），词级延迟要用对齐脚本实测。

### 4.2 RNN-T 的流式化

* Transducer 的解码沿时间轴同步推进，**天然流式**；瓶颈仅在 encoder 的双向注意力，做 chunk 化即可。
* 工程优化：**Stateless Predictor**（去掉 LSTM，只用最近 2~3 个 token 的 Embedding/Conv）显著降低单步延迟；**Pruned RNN-T**（如 k2 pruned transducer）把 $(T \times U)$ 联合计算裁剪为每个编码帧只保留 top-k 竞争路径，训练和解码都更快。
* **延迟惩罚训练**（Fast-RNNT 的 delay-penalized loss）：在损失中加入发射时刻惩罚项

$$\mathcal{L} = \mathcal{L}_{\text{RNNT}} + \lambda \cdot \mathbb{E}_{\text{path}}[\,t_{\text{emit}} - t_{\text{align}}\,]$$

  显式把"更早出字"写进目标，可把词级延迟再压 100~300ms 而几乎不损 WER。

### 4.3 AED 的流式化

AED 的 Decoder 自回归且 Cross-Attention 全局，是最难流式化的架构，主要路线：

1. **Wait-k / 单调注意力（MMA）**：读到第 $k$ 帧才输出第 1 个 token，此后每读一帧写一帧，强制读写同步；simulWhisper 把该策略移植到 Whisper（利用其时间戳 token 做读写对齐决策）。
2. **Chunk-based Cross-Attention**：Decoder 的 K/V 限定在已产出的 chunk 编码结果内，本质是 encoder chunk 化 + 受限注意力。
3. **2-pass（级联重打分）**：流式分支（RNN-T/CTC）实时出 partial，endpoint 后用 offline 分支（AED/大模型）对整句重新解码并替换 final——阿里 FunASR 的 Seaco-Paraformer 2-pass、Google 的 cascade encoder 均属此类，是"低延迟 + 高精度"的工业标配。
4. **CIF 类方案**：Paraformer 的流式版本用 CIF（Continuous Integrate-and-Fire）预测器按块积分声学证据，实现块级单调出字。

### 4.4 综合对比

| 维度 | CTC | RNN-T | AED |
| --- | --- | --- | --- |
| **流式改造点** | 仅 encoder chunk 化 | 仅 encoder chunk 化（解码天然流式） | encoder + decoder 双重受限（wait-k/单调注意力/2pass） |
| **解码驱动** | 帧同步 | 帧同步（时间-文本 2D） | 文本自回归 |
| **语言模型能力** | 弱，需外部 LM | 内置（Prediction Net） | 最强（Decoder 即 LM） |
| **词级延迟** | 低，但峰值滞后 100~300ms | 低，可加 delay penalty 压缩 | 中高，受 wait-k 与逐 token 生成限制 |
| **回改能力** | 弱（帧同步输出难撤回） | 中（beam 随 chunk 更新可回改） | 强（整句重写，天然适合 2pass final） |
| **典型代表** | WeNet U2-CTC、Zipformer-CTC | Zipformer/Conformer Transducer | simulWhisper、Paraformer-streaming、2pass |

## 5. 有限上下文窗口（LCBL）与块间信息丢失

### 5.1 LC-BLSTM：有限上下文窗口的经典实现

Google 2019 年的端侧流式 RNN-T（He et al.）把 encoder 从 BLSTM 换成 **LC-BLSTM（Limited-Context BLSTM）**：前向 LSTM 正常看全历史，后向 LSTM **只回看有限未来**——每个后向层从"往后看 $R$ 帧"的窗口出发运行。堆叠 $L$ 层后，等效 lookahead 随深度线性增长：

$$T_{\text{lookahead}}^{\text{eff}} = L \cdot R \cdot \Delta t \quad (\text{如 } 8 \text{ 层} \times 25\text{ms} = 200\text{ms})$$

这是"有限上下文窗口"思想的鼻祖：**用深度换上下文**——层与层错位叠加，让高层神经元间接看到更远的未来，而不增加单层延迟。现代 chunk-based attention 的"chunk + lookahead + 左上下文"窗口设计是同一思想在 Transformer 上的延续。

### 5.2 块间信息丢失问题

把音频切成独立 chunk 会带来三类损伤：

1. **跨块长依赖断裂**：协同发音、跨 chunk 的词组（如英文跨块的三词短语）、语调与说话人信息无法穿透 chunk 边界；
2. **边界帧表征劣化**：chunk 首尾帧缺少两侧完整上下文，其输出错误率显著高于 chunk 中部帧，表现为**块边界处的删除/插入错误聚集**；
3. **训练-推理不一致**：若训练用全上下文、推理用受限上下文，表征分布漂移会带来明显 WER 上升（流式部署必须做 limited-context 训练或微调）。

### 5.3 缓解策略

| 策略 | 做法 | 代价 | 效果 |
| --- | --- | --- | --- |
| **Chunk Overlap（块重叠）** | 相邻 chunk 重叠 $O$ 帧，只取每块中部输出 | 计算量变为 $\frac{C+O}{C}$ 倍 | 平滑边界，简单有效 |
| **Stacking / 多分辨率** | 相邻帧 stack 后再编码（Zipformer 的多帧率 zip 结构） | 帧率设计复杂 | 增大等效感受野且不增延迟 |
| **State Passing（状态传递）** | 卷积尾帧缓存、attention K/V cache、LSTM hidden、Emformer memory 摘要跨 chunk 传递 | 会话状态管理复杂 | 无损保留左上下文，当前主流 |
| **随机 chunk 训练** | 训练时随机化 chunk/lookahead 大小（dynamic chunk），或 offline 预训练 + 流式微调 | 训练流程更长 | 消除训练-推理失配，一模型多档延迟 |
| **2-pass 回改** | 流式 partial + offline 重打分 final | 服务器双份计算 | final 精度逼近 offline |

> **面试高频**："为什么 chunk 变小 WER 会掉？"——答三层：右上下文不足（音素切分信息不够）、左上下文截断（历史语言/声学线索丢失）、边界帧劣化；再分别对应 lookahead、state passing/cache、overlap 三类缓解手段。

## 6. 流式解码细节：延迟输出、Stabilization 与 Endpointing

### 6.1 Partial 假设与延迟输出

流式系统每个 chunk 结算一次 **partial hypothesis**（当前最优句子的前缀），随语音推进增量刷新。真实出字延迟由三部分叠加：

$$T_{\text{token}} \approx T_{\text{algo}} + T_{\text{acoustic-peak}} + T_{\text{eng}}$$

其中 $T_{\text{acoustic-peak}}$ 是模型分布峰值滞后于真实发声边界的量（CTC/RNN-T 通常 100~300ms），这也是 delay penalty 训练要压缩的对象。评估流式系统不能只看 WER，必须同时画 **WER-Latency 曲线**（横轴词级延迟，纵轴 WER）。

### 6.2 Stabilization（回改）机制

partial 是"当前上下文下的最优猜测"，新 chunk 到来后**前缀可能改变**（chunk 边界处的字被修正、beam 排序翻转、RNN-T 的发射回退）。前端展示必须处理这种不稳定性：

```
语音:      │今 天 ── 天 气 ── 真 好 ────(尾静音 800ms)────│
chunk:      c1       c2       c3      c4            ▲ endpoint 触发
partial:   "今天"  "今天天气" "今天天启"→"今天天气真好"    final: "今天天气真好。"
                    (c2 曾回改 c1 的末字; c3 出现错字, c4 修正)  (前缀锁定, 不再变化)
```

* **上屏策略**：常见做法是"已上屏的稳定前缀（如距当前 chunk 超过 $k$ 个字）不可回改，只允许修改最近 $N$ 个字"，在稳定性与正确性间折衷；
* **Final 化**：endpoint 触发后用完整上下文（+可选 LM rescore / offline 分支）重新解码整句，替换屏幕上的 partial，此后文本锁定；
* **AED/2pass 场景**：final 整句重写是常态，前端需要支持"替换式"渲染而非"追加式"。

### 6.3 Endpointing 与 VAD 切分

判定"用户说完了"的机制，直接决定尾部延迟与断句体验：

1. **内嵌 endpoint detector**：在流式解码内部根据 CTC/RNN-T 输出帧的语音活动后验做平滑判决，规则形如

$$\text{if } \text{silence} \ge \theta_{\text{tail}} \text{ and } \text{speech} \ge \theta_{\text{min}} \Rightarrow \text{finalize}()$$

   典型参数：尾静音阈值 $\theta_{\text{tail}}$ = 500~800ms，最短语音 100~250ms，最长语音 10~30s 后强制切分（长句保底，切分点回退到最近的深静音处）；
2. **外部 VAD 预切分**：独立神经 VAD（Silero、WebRTC VAD，10~20ms 帧级）先切出语音段再送识别器，适合会议/直播等长音频；缺点是双系统状态同步复杂、VAD 误切会截断词；
3. **坑点**：语气词（"嗯""啊"）、呼吸声导致误 endpoint；语速快的人尾静音短需要更小的 $\theta_{\text{tail}}$（代价是更容易截断拖长音的词）；多轮对话中通常把 $\theta_{\text{tail}}$ 与语义完整度（标点/句法）联合判决。

## 7. 流水线并行与 Cache-aware Decoding

### 7.1 Cache-aware（K/V 缓存）推理

朴素做法下，第 $i$ 个 chunk 若要看到历史左上下文就得把历史帧重新编码一遍，总计算量为 $O(T^2)$ 级。**Cache-aware decoding** 把历史 chunk 的 K/V（以及卷积尾帧、RNN 状态等）缓存复用，每个 chunk 只计算自己的 query：

$$\text{Attn}(Q_c,\ [K_{\text{cache}};K_c]) \cdot [V_{\text{cache}};V_c]^{\top}, \quad K_c,V_c \text{ 计算完追加进 cache}$$

* 单 chunk 计算量降为 $O\big(C\cdot(L_{\text{left}}+C)\big)$（$C$ 为 chunk 长、$L_{\text{left}}$ 为保留的左上下文长），历史完全不重算；
* 需要缓存的完整状态清单：下采样卷积尾帧、每层 attention 的 K/V、深度卷积尾帧、（RNN-T 的）predictor 递归状态、（Emformer 的）memory 摘要——这些就是 5.3 节的 state passing 的推理态实现；
* LLM 推理里的 PagedAttention/前缀缓存思想可直接迁移到 ASR 服务端。

### 7.2 Chunk 级流水线并行

把"收包/特征提取（CPU）→ 编码前向（GPU）→ 解码/上屏（CPU）"三级流水，相邻 chunk 重叠执行：

```
时刻 ──►
收包+特征(CPU): │-f1-│     │-f2-│     │-f3-│     │-f4-│
编码前向(GPU):        │==E1==|    │==E2==|    │==E3==|
解码上屏(CPU):               │d1│      │d2│      │d3│
                稳态吞吐 ≈ 1 / max(T_feat, T_infer, T_decode)
```

若无流水线，三段延迟串行累加；流水后稳态吞吐由最慢一级决定，端到端延迟约等于单 chunk 的最长一级 + 一个 chunk 周期。

### 7.3 GPU Chunk 合并（Dynamic Batching）

单路流式请求每个周期只有一个几百毫秒的 chunk，GPU 利用率极低（<5%）。服务端做法：

* 把**多个并发请求"当前时刻的 chunk"** 按帧数对齐（pad/truncate 到统一 chunk 长度）后合并成一个 batch 一次前向，batch 内各请求各用各的 cache；
* 配合动态 batching（攒批窗口通常 ≤ 1 个 chunk 周期，如 100~200ms，避免引入额外延迟）；
* 代价是 batching 等待与 padding 浪费，但单卡吞吐可提升 **3~10 倍**，是流式 ASR 服务（如 WeNet runtime、FunASR server）的标配；端侧则是单请求 + 量化（INT8）+ 算子融合，CPU RTF 可做到 0.1~0.3。

## 8. Chunk 大小的延迟-准确率权衡

以中文 4x 下采样（编码帧 40ms）、Conformer/Zipformer + RNN-T 为例的经验量级（WER 为相对 offline 基线的相对劣化，供量级参考）：

| chunk 时长 | lookahead | 算法延迟（上界） | WER 相对劣化 | 适用场景 |
| --- | --- | --- | --- | --- |
| 160ms | 0~80ms | 160~240ms | +35%~50% | 输入法、极低延迟助手 |
| 320ms | 160ms | ~480ms | +20%~35% | 语音助手、智能音箱 |
| 640ms | 160~320ms | ~800~960ms | +10%~20% | 会议实时字幕（常用默认） |
| 960ms~1s | 320~640ms | 1.3~1.6s | +5%~10% | 直播字幕、对延迟不敏感场景 |
| offline（全句） | 全句 | 秒级 | 0（基线） | 离线转写 |

规律与选型建议：

* **WER 劣化对 lookahead 最敏感**：0 lookahead 时削峰、插入错误暴增；加 160~320ms lookahead 能吃掉大半劣化，是"性价比最高的延迟"；
* chunk 从 640ms 再往上增大，精度收益边际递减，而首包延迟线性变差；
* 中文（字级 token）对右上下文的敏感度略低于英文（BPE 词片更长、跨 chunk 概率更高）；
* 用 **dynamic chunk 训练**让一个模型支持多档 chunk，部署时按业务延迟预算选档，避免训练多套模型。

## 9. PyTorch 代码实战：Chunk 流式推理会话

以 Chunk-based Conformer + CTC 为例，演示 cache-aware 编码、增量解码、stabilization 与 endpoint 的完整闭环（RNN-T 场景只需把第 4 步换成 transducer 增量解码，predictor 状态同样入 cache）。

```python
import torch

def build_chunk_attn_mask(T: int, right: int, device):
    """构造 chunk 流式注意力 mask: 可见 = 过去全部(经cache) + 当前位置右侧 right 帧"""
    idx = torch.arange(T, device=device)
    visible = idx[None, :] <= idx[:, None] + right   # [Q, K]: query i 可见 key <= i+right
    return (~visible).float() * float("-inf")        # 不可见位置填 -inf

class StreamingSession:
    """单路流式识别会话: 每 ~160ms 调用一次 feed(), 维护全部跨 chunk 状态"""
    def __init__(self, model, blank_id=0,
                 chunk=16,        # 16 个编码帧 = 640ms
                 right=8,         # lookahead 8 帧 = 320ms
                 subsample=4,     # 编码帧 = 4 x 10ms
                 endpoint_sil=800.0):  # 尾静音 800ms 判 endpoint
        self.model, self.blank = model, blank_id
        self.chunk, self.right, self.sub = chunk, right, subsample
        self.frame_ms = 10 * subsample                       # 40ms
        self.endpoint_frames = int(endpoint_sil / self.frame_ms)
        self.feat_buf = None      # 10ms 帧缓冲 (凑整 chunk 用)
        self.attn_cache = [None] * model.num_layers          # K/V cache (state passing)
        self.conv_cache = [None] * model.num_layers          # 深度卷积尾帧缓存
        self.prev_tok, self.prev_frame_tok = None, None      # CTC 去重状态
        self.emitted, self.pending = [], []                  # 稳定前缀 / 可回改尾部
        self.silence = 0

    @torch.no_grad()
    def feed(self, feats: torch.Tensor) -> dict:
        """feats: 本周期新到的 Fbank 帧 [n, 80] (10ms/帧); 返回 partial/final 事件"""
        self.feat_buf = feats if self.feat_buf is None \
                        else torch.cat([self.feat_buf, feats])
        out = {"partial": None, "final": None, "endpoint": False}

        # 1. 凑满一个 chunk 的输入帧 (chunk*sub 个 10ms 帧 + 3 帧下采样卷积 lookahead)
        need = self.chunk * self.sub + 3
        while self.feat_buf.size(0) >= need:
            enc_in = self.feat_buf[:need]
            self.feat_buf = self.feat_buf[self.chunk * self.sub:]  # 余量留给下一 chunk

            # 2. cache-aware 编码: 只前向当前 chunk, K/V 从 cache 恢复并更新
            logits, self.attn_cache, self.conv_cache = self.model.encoder.forward_chunk(
                enc_in, self.attn_cache, self.conv_cache, self.right)  # [chunk, V]

            # 3. 增量 CTC 解码 (帧同步 argmax + 去重去 blank)
            for frame in logits.argmax(-1).tolist():
                self.silence = self.silence + 1 if frame == self.blank else 0
                if frame != self.blank and frame != self.prev_frame_tok:
                    self.pending.append(frame)             # 新 token 先进可回改区
                self.prev_frame_tok = frame

            # 4. 稳定性处理: 距离 pending 末尾超过 4 个 token 的部分锁定为稳定前缀
            if len(self.pending) > 4:
                self.emitted += self.pending[:-4]
                self.pending = self.pending[-4:]
            out["partial"] = "".join(self.model.tokens(self.emitted + self.pending))

            # 5. Endpoint: 尾静音超阈值 -> 整句 finalize (可在此接 LM rescore / offline 2pass)
            if self.silence >= self.endpoint_frames and (self.emitted or self.pending):
                final_ids = self.emitted + self.pending
                out["final"] = "".join(self.model.tokens(final_ids))
                out["endpoint"] = True
                self._reset()                              # 清空全部状态, 开启下一句
        return out

    def _reset(self):
        self.feat_buf, self.prev_tok, self.prev_frame_tok = None, None, None
        self.attn_cache = [None] * self.model.num_layers
        self.conv_cache = [None] * self.model.num_layers
        self.emitted, self.pending, self.silence = [], [], 0

# 使用示意: pcm -> 10ms Fbank -> 每 160ms feed 一次
# session = StreamingSession(model)
# for block in pcm_stream:                      # 实时音频块 (如 100~300ms)
#     ev = session.feed(extract_fbank(block))   # 特征提取与前向流水重叠 (见 7.2 节)
#     if ev["partial"]: render(ev["partial"])   # partial 可回改最近几个字
#     if ev["final"]:   commit(ev["final"])     # final 锁定整句
```

配套的 `encoder.forward_chunk` 内部逻辑（伪代码）：下采样卷积拼接上一 chunk 的 3 帧尾帧 → 各层用 `build_chunk_attn_mask` 做 cache-aware attention（当前 chunk 的 Q 对 `[K_cache; K_cur]` 计算，左上下文无限）→ 更新并返回两类 cache。

## 10. 总结与最佳实践

* **延迟口径先行**：区分首包/词级平均/尾部、算法延迟/工程延迟；算法延迟上界 $= (\text{chunk} + \text{lookahead})$，工程延迟靠流水线、batching、量化压缩。
* **架构选型**：RNN-T（尤其 Zipformer + Pruned/stateless）是低延迟流式的首选；CTC 实现最简单但缺 LM；AED 直接流式化最困难，工业上多以 **2-pass（流式 partial + offline final 重打分）** 落地。
* **上下文设计**：lookahead 的精度性价比最高（160~320ms 基本必备）；左上下文用 **state passing / K/V cache** 无损传递（Emformer memory 是其有损变体）；chunk overlap 与多分辨率 stacking 用于缓解边界帧劣化。
* **训练-推理一致**：必须做 limited-context / dynamic chunk 训练（或 offline 预训练 + 流式微调），否则上线 WER 明显回退；delay penalty 训练可再压缩词级延迟 100~300ms。
* **解码与交互工程**：partial 支持受限回改（锁定稳定前缀），endpoint 用尾静音 500~800ms + 最短/最长语音三阈值，长音频配外置 VAD 兜底；评估必须同时报 WER 与 WER-Latency 曲线。
* **服务化**：多请求 chunk 动态合并 batch 提升 GPU 利用率 3~10 倍，配合 K/V cache 与 PagedAttention 思想做高并发流式服务；端侧走 INT8 量化 + 因果算子融合，CPU RTF 0.1~0.3 可用。
* **演进方向**：统一流式/非流式模型（U2、dynamic chunk）、语音 LLM 的流式化（wait-k、chunk 级 speech token、2pass 校正）是当前面试与研发的共同热点。
